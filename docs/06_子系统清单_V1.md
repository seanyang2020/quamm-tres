## 2. 六条边界约定（写给开发）

| # | 约定 | 违反后的后果 |
|---|---|---|
| 1 | 入口（S1/S2）只调业务，**不直连数据库** | 绕过业务规则，冲突检测失效 |
| 2 | 业务之间只通过领域方法调，**不互相拼 SQL** | 两处各自实现同一规则，一定跑偏 |
| 3 | **S5 与 S6 必须共享一个事务**：授予成功与出队、回收与发 offer 要在同一事务里完成 | 会出现"资源已释放但队列没被唤醒"，排队者永远等不到 |
| 4 | S7 只改**设备状态**，不改租约（掉线不回收，标 degraded） | 网络抖动会误杀正在跑的长任务 |
| 5 | S8 是唯一允许人工改判的入口，**任何自动流程不能"假装自动"绕过它** | 身份错了、冲突了还硬猜，数据会静默错挂 |
| 6 | S12 只负责"到点触发"，**不做业务判断** | 业务规则散落到定时任务里，之后无法统一修改 |

## 3. 三条主链路

### 链路 A：AI 申请（MCP）

```
MCP 客户端 → S2 → S9 鉴权与配额校验
                    → S5 查空闲（按平台/指定设备）
                        ├ 有 → 加锁 → 写租约 → S3 更新状态
                        │        → S10 发事件 → 返回 lease + adb_address + ports
                        └ 无 → S6 入队 → 返回 ticket + 位次 + 预计等待
```

### 链路 B：释放与唤醒（最容易出 bug 的一步）

```
S5 回收（release / 超期 / 强制）
  └→ 同一事务内通知 S6
       └→ S6 给队首发 offer，资源进入 RESERVED（60s）
            ├ 队首 confirm → S5 授予 → S10 通知双方
            └ 超时/拒收 → S6 顺延下一位，资源继续 RESERVED
```

### 链路 C：巡检与人工恢复

```
S12 每 15/30 min 触发 → S7 探测四级
  ├ L3 正常 → 无动作（只在状态变化时写流水）
  ├ L0 ICMP 不通 → 连续 2 轮 → 判 offline → S10 通知维护责任人
  ├ L1 端口不通 + 历史是 L3 → 连续 2 轮 → 判 suspect_data_wiped → 通知恢复指引
  ├ L2 unauthorized → 判 keys_lost → 通知重新预置 adb_keys
  └ 恢复 L3 → 自动回 available → S10 发"已恢复"
```

## 4. 人工介入的五个触发点（S8 的全部职责）

| # | 触发 | 现象 | 人工做什么 | 系统给什么支撑 |
|---|---|---|---|---|
| 1 | 待认领 | 新设备无强锚命中 | 命名、定位置编号、贴资产标签 | 候选列表 + 命中信号 + 置信度 |
| 2 | 疑似 data 被擦 | 原 L3 → L1 持续 2 轮 | 重刷钩子 + 重放 adb_keys | 恢复步骤指引 + 一键重试探测 |
| 3 | 强锚冲突 | 同 MAC / 同 SN 出现两个活跃实例 | 确认哪台是真的，另一台隔离 | 两台并排对比 + 最近活动时间 |
| 4 | 疑似换板 | 强锚全失效、位置命中 | 确认后把资产标签迁到新硬件 | 差异清单（旧 vs 新） |
| 5 | 强制回收 | 超期占用 / 异常占用 | 填原因、通知原持有人 | 占用时长 + purpose + 当前状态 |

**设计原则**：这五件事**不做自动化猜测**。系统负责把"判断所需的信息"摆到人面前，人点一下即可 —— 自动猜错一次的成本（历史错挂、租约挂错设备、统计失真）远高于点一下的成本。

## 5. 带屏 / LED 设备的辅助物理确认（S8 的增强）

你的想法是对的：网络指纹永远有不确定性，物理确认是最后一道保险。把它做成**可点击的操作**，而不是靠人在群里问。

| 设备类型 | 确认手段 | 实现方式 |
|---|---|---|
| 带屏设备 | 在屏幕上显示设备编号 / 位置编号 | `adb shell` 执行预置脚本，全屏显示一段文字（如 `D-0007 / 302-R2-05`） |
| 带 LED 设备 | 闪灯 / 点亮指定颜色 | `adb shell` 写 LED sysfs 节点，或调用预置识别脚本 |
| 无屏无灯的板子 | 只能靠位置编号 + 拔插/串口打印 | 巡检日志 + 人工按位置核对 |

使用方式（在 Web 的"待认领"或"冲突处理"页）：

1. 选中一台候选设备 → 点"点亮 / 显示编号"
2. 现场的人看到灯闪或屏幕显示，确认"是不是这台"
3. 点"确认" → 写 `identity_event`（人工确认、操作人、时间）→ 该设备身份置信度提升，转 `available`

**注意**：这只是**辅助手段**，不进自动判定链。自动匹配永远只认强锚；物理确认只在"人做裁决"时提供依据。

## 6. 巡检节奏与误刷恢复（按你的口径）

| 项 | 取值 |
|---|---|
| 巡检周期 | **15 或 30 分钟，可配**（默认 30） |
| 判离线 | 连续 2 轮失败 |
| 判 data 被擦 | 原 L3 → L1，连续 2 轮（ICMP 正常） |
| 恢复方式 | 人工重刷钩子 + 重放 adb_keys → 下一轮巡检自动回 `available` |
| 通知对象 | 设备维护责任人（按平台分配），设备被占用时同时通知占用人 |

## 7. 本期明确不做（边界）

| 不做 | 原因 |
|---|---|
| 网段隔离 / 5555 访问控制 | 设备都在局域网内，本期接受该风险，记录在案（见 05 文档 §2.1，已降级） |
| 计费、结算 | 内部使用，无结算需求 |
| CI 流水线调度、自动化测试编排 | 本系统只分配资源，不做任务编排 |
| 预约未来时段 | 与即时排队是两种语义，二期单独设计 |
| 多租户隔离与外部客户计费 | 一期先服务内部 |
