# 第一部分：规则清单

## A 域｜设备注册与身份识别（2026-11-07 按实际量级重写）

> 前置：约 15 类设备、每类 ≤50 台，合计 500–750 台，**全部走网络 ADB（tcp 5555）**，不做 USB 直连。详细方案见 `04_设备注册与身份识别方案_V1.md`。

| 编号 | 规则 | 为什么 | 状态 |
|---|---|---|---|
| R-A1 | 主键是系统内部 `device_id`，创建后永不变；MAC / SN / 硬件 ID 是"识别锚点 + 唯一索引"，不是主键 | "同一 MAC = 同一台"的语义用唯一索引一样能保证；但 MAC 会被刷机擦掉，做成主键会在全擦那天把历史占用记录撕成两半 | 待确认（与你的表述有差异，见回复说明） |
| R-A2 | MAC 归一化（小写、去 `:`/`-`）后建唯一索引：一个 active MAC 只能属于一台设备 | 不同来源格式不一致会把同一台认成两台 | 已定 |
| R-A3 | 设备分四型，按型选锚点：A 型（MAC 稳）主锚 MAC；B 型（SN 稳）主锚 SN；C 型（两者都不稳）主锚自建资产文件、辅以位置；D 型（全无）只能人工认领 | 存在"部分机型用 SN、部分用 MAC、还有只能动态探测"的情况，不能一刀切 | 已定 |
| R-A4 | 每台设备必须录入**物理位置**（机架-层-位 / 工位号）和**资产标签**，二者不随刷机变化 | 全擦时 MAC、SN、固件全失效，位置和贴纸是唯一还能用的锚 | 已定 |
| R-A5 | 标识变化不新建设备：旧标识声明置 `retired`，新声明挂到原 `device_id`，记 `drifted` 事件 | 这是"全擦不断历史"的实现方式 | 已定 |
| R-A6 | 匹配打分三档：强锚（资产文件/硬件ID/MAC/SN）命中即自动认定；无强锚但弱信号累计 ≥60 进待确认；<60 新建 `pending_identity` | 自动猜错的代价（历史错挂、租约挂错设备）远高于让人点一下 | 已定 |
| R-A7 | 同一强锚出现两个活跃实例（MAC 被克隆）→ 判 `conflict`，两台同时暂停入池并告警 | 显式处理，否则两个物理设备会抢同一条台账 | 已定 |
| R-A8 | IP 是易变属性（DHCP），不参与身份，只存 `current_ip` / `last_seen_at` | IP 会变，做进身份会让身份随 IP 漂移 | 已定 |
| R-A9 | 网络 ADB 的 adb serial 通常是 `ip:5555`，**不是设备身份**，只能作当前接入点 | 拿它当身份，IP 一变就认成新设备 | 已定 |
| R-A10 | 探测结果分四级：L0 ICMP 不通 / L1 端口不通 / L2 unauthorized / L3 shell 可用；**只有 L3 能入池** | 四级对应四种维护动作，混成一个"离线"会制造大量无效排查 | 已定 |
| R-A11 | `pending_identity` / `pending_probe` 状态的设备不参与申请分配 | 宁可少几台可用，也不能让身份不明的设备被占走 | 已定 |
| R-A12 | `maintenance` / `offline` 不可申请；有活跃租约时不能直接改状态 | 避免"资源已下线但租约还在跑" | 已定 |
| R-A13 | 所有 发现 / 匹配 / 漂移 / 冲突 / 认领 动作都落 `identity_event` 流水 | 事后能回答"这台设备的身份是怎么变的" | 已定 |

**刷机导致的四种身份变化**：新镜像（强锚不变，自动认定）· 擦 SN（MAC 锚命中，自动）· 全擦（双锚失效，位置锚 + 人工确认）· 换板（全锚失效，位置命中，人工确认后迁移资产标签）。详见 04 文档第 7 节。

## B 域｜租约（Lease）

| 编号 | 规则 | 为什么 | 状态 |
|---|---|---|---|
| R-B1 | 任何占用都必须来自一条有效租约；无租约的访问在策略层视为非法 | 这是"可管控"的定义本身，否则一切回到人工口头协调 | 已定 |
| R-B2 | 租约必含：`lease_id`、`device_id`、`port_ids[]`、`holder`、`purpose`、`ttl`、`expires_at`、`state` | `purpose` 让审计能回答"占着干什么" | 已定 |
| R-B3 | 授予后按 TTL 倒计时；holder 可主动续约（MCP `res_renew`）顺延到期时间 | 长任务不用反复申请 | 已定 |
| R-B4 | TTL 到期前提醒（续约提示 + 看板标黄 + 可选企微/飞书消息），提醒不中断任务 | 提前告知比事后硬回收重要 | 已定 |
| R-B5 | TTL 到期转 `EXPIRING` 进入宽限期（默认 10 分钟），期间资源仍可用，续约即恢复 `ACTIVE` | MCP 是短调用，Agent 在刷机/验证期间不会持续调工具，纯心跳会误杀长任务 | 已定 |
| R-B6 | 宽限期结束仍无续约 → 强制回收、唤醒队列、通知原 holder | 僵尸占用必须有终点 | 已定 |
| R-B7 | 不做高频心跳：租约存活靠 TTL + 主动续约 + 宽限期三重兜底 | MCP 场景下"heartbeat 每 30s"不可实现，写进需求会让开发做出一个跑不通的系统 | 已定 |
| R-B8 | 连接断开 ≠ 释放；只有显式 `release`、宽限期结束、管理员强制回收三种方式结束租约 | 连接断了但任务还在跑是常态；断开即释放会把任务中途踢掉 | 已定 |
| R-B9 | `release` 幂等：重复释放返回成功而非 404，释放不存在的租约返回明确原因 | 客户端清理逻辑常被重放 | 已定 |
| R-B10 | `apply` 幂等：同一 holder + 同 target + 短时间窗内重复提交，返回同一租约或同一票据 | MCP 客户端重试是常态，不能重复占号 | 已定 |
| R-B11 | 单个 holder 同时持有的活跃租约数上限默认 2，可配 | 防止一个人或一个助手把池子扫光 | 待确认（数值） |
| R-B12 | 到期提醒阈值可配（按 TTL 比例或固定分钟，默认到期前 10 分钟） | 不同长度的任务需要不同提前量 | 待确认 |
| R-B13 | 服务端时间为唯一判定基准，客户端时间不参与任何到期计算 | 各机器时钟不同步会导致误判 | 已定 |
| R-B12 | 租约状态在服务重启后完整恢复，不因重启丢失 | 否则重启即"全部资源凭空释放" | 已定 |

## C 域｜排队与唤醒

| 编号 | 规则 | 为什么 | 状态 |
|---|---|---|---|
| R-C1 | 支持两种排队：按"资源组"排队（调度时挑组内任一空闲）、按"指定 `device_id`"排队（我就要这台） | 前者的价值是单台坏了不卡队列；后者满足"已刷好我镜像的那台" | 待确认（V1 是否两种都做） |
| R-C2 | 排序：`priority` 高的优先；同 `priority` 按入队时间升序（严格 FIFO） | 保证可解释，避免"看谁手快" | 已定 |
| R-C3 | V1 不做抢占：高优先级不能踢掉正在跑的租约，只影响排队顺序 | 抢占会带来任务被中途打断，代价远高于收益 | 待确认 |
| R-C4 | 资源释放后**只向队首发放 `offer`**，租约进入 `RESERVED`，确认窗口默认 60s | 广播"先到先得"会引发惊群，多人同时抢一台 | 已定 |
| R-C5 | 队首在窗口内 `confirm` → `GRANTED`；超时或显式拒收 → 顺延下一位，并通知双方 | 防止队首是僵尸 Agent把资源卡死在 RESERVED | 已定 |
| R-C6 | `RESERVED` 期间，该资源对其他申请者一律显示为不可用 | 避免 offer 期间被第三方抢走 | 已定 |
| R-C7 | 排队者可设"最长等待时间"，超时自动出队并通知，不留在队列里占位 | 清理僵尸排队 | 待确认（要不要做） |
| R-C8 | 队列位置变化（前进、被 offer、被顺延）都要推送事件 | 不然排队者只能靠刷新 | 已定 |
| R-C9 | 队列序号原子分配，同一时刻不允许两个申请拿到相同位次 | 并发下位次错乱无法排查 | 已定 |
| R-C10 | 出队/取消要区分原因：主动取消、超时、已获得、被管理员移出 | 审计能回答"为什么没拿到" | 已定 |

## D 域｜独占与冲突

| 编号 | 规则 | 为什么 | 状态 |
|---|---|---|---|
| R-D1 | `exclusive` 资源在同一时刻全局唯一租约 | 核心不变量 | 已定 |
| R-D2 | `shared` 资源按 `max_holders` 计数，超出拒绝或排队 | 有些设备支持多路并行调试 | 待确认（V1 是否需要） |
| R-D3 | 申请设备时，默认连带锁定其全部串口（一并进入同一租约） | 防止"A 拿设备、B 拿串口"互相打断，这是最常见的现场冲突 | 已定（默认值待确认是否可放开） |
| R-D4 | 单独申请串口时，若其宿主设备已被 `exclusive` 租用，直接拒绝并说明占用人 | 同上，双向都要堵 | 已定 |
| R-D5 | 授予走行锁/乐观锁，禁止"最后一台设备被两个请求同时拿到" | 典型并发超发 | 已定 |
| R-D6 | 一条租约可整体持有多个串口；不支持把同一设备的串口拆给不同 holder（除非该组显式配置允许） | 简化状态，避免串口级细碎冲突 | 待确认 |

## I 域｜巡检与设备健康（2026-11-07 新增，先定策略）

| 编号 | 规则 | 状态 |
|---|---|---|
| R-I1 | 巡检周期 30 分钟一轮，整池统一节奏，不做每台设备独立定时 | 待确认（周期值） |
| R-I2 | 每台设备绑定"维护责任人"字段，掉线通知发给该责任人，而不是只发给管理员一人 | 待确认（责任人怎么分配） |
| R-I3 | 全部设备走网络 ADB，探测按四级递进：ICMP → 5555 端口 → `adb devices` 授权状态 → `adb shell` 可用；串口另用 SerialBridge 握手 | 已定（策略） |
| R-I4 | 单轮探测并发上限默认 5，单次超时 adb 5s / ping 2s，避免百台设备同时探测打爆网络 | 待确认（数值） |
| R-I5 | 单轮失败 → `suspect`（只标黄、不通知）；连续 2 轮失败（≈60 分钟）→ `offline`，发维护通知 | 已定 |
| R-I6 | 掉线通知必须带：设备名、位置、维护责任人、上次在线时间、连续失败次数、建议排查动作 | 已定 |
| R-I7 | 设备掉线时若正被占用，必须**同时通知当前占用人**；其 MCP 下一次调用返回"你的设备已掉线" | 已定（关键，否则占用人会白等） |
| R-I8 | 探测恢复成功（1 轮）即自动转 `available`，并发"已恢复"通知，不需要人工确认 | 已定 |
| R-I9 | 掉线不改变租约状态：活跃租约保留并标 `degraded`（与 R-F2 一致），不自动回收 | 已定 |
| R-I10 | 巡检只影响可用性标记与告警，不参与排队调度；`offline` 设备不参与新申请分配 | 已定 |
| R-I11 | 每轮巡检结果都要落流水（成功 / 失败 / 耗时），用于事后判断"这台是不稳定还是真坏" | 已定 |
| R-I12 | 通知渠道：企业微信 / 飞书为主，Web 看板红点为辅；同一设备 2 小时内不重复轰炸，只在状态变化时发 | 待确认 |

**为什么是 30 分钟而不是 5 分钟**：巡检的目的不是实时监控，而是"别让人对着一台死设备白等半天"。30 分钟足以在半小时内发现掉线，同时把探测开销压到可忽略（100 台设备约每分钟 3 台）。需要更快感知的场景（正在被占用的设备）由占用人自己调用失败来兜底，不依赖巡检提速。

**这一域只写策略，实现放到后面**：巡检器作为独立进程（定时任务），与租约引擎解耦，只读写设备状态，不改租约。

## J 域｜入口与单一事实来源（2026-11-07 新增）

| 编号 | 规则 | 为什么 | 状态 |
|---|---|---|---|
| R-J1 | **唯一事实来源**：设备状态、租约、队列只在中心服务存一份；Web 与 MCP 都是视图，任何一方都不许拿自己的缓存当判定依据 | 双入口最常见的故障就是"Web 显示空闲、MCP 说没资源" | 已定 |
| R-J2 | **双入口共用同一业务逻辑**：Web 的"申请/释放"按钮与 MCP 的 `res_apply`/`res_release` 调同一个内部服务方法，禁止各写一套 | 两套实现必然在冲突检测、配额、队列顺序上产生分歧，且很难发现 | 已定 |
| R-J3 | **注册与注销统一**：只有中心能注册/下线设备；Web 管理页与 MCP 管理工具都调同一接口 | 允许旁路注册，就等于放弃台账的唯一性 | 已定 |
| R-J4 | **查询同源**：MCP 的 `res_list_devices` 与 Web 看板读同一份数据；可用性由服务端统一计算（含 pending / offline / 过期租约 / 已被 offer 预留） | 可用性若在两端各自算，结果必然不一致 | 已定 |
| R-J5 | `pending_identity` / `pending_probe` / `offline` / `RESERVED` 的设备，在 MCP 与 Web 上都显示为不可申请，措辞允许不同但结论必须一致 | 避免 Agent 申请到 Web 上明明标着"不可用"的设备 | 已定 |
| R-J6 | **配额跨入口合计**：同一个 holder 无论从 Web 还是 MCP 申请，并发上限合并计算 | 否则人可以 Web 占 2 台、再用 Agent 占 2 台，绕过上限 | 已定 |
| R-J7 | 同一状态变化对两端的可见延迟都 ≤2s；Web 靠 WS 推送，MCP 每次调用直读最新状态 | 双端不同步会引发重复申请和误判 | 已定 |

**中心与两入口的职责边界**

| | Web（人） | MCP（AI） |
|---|---|---|
| 查询 | 全量看板、占用墙、队列、审计 | 可用设备、自己的租约、队列位次 |
| 变更 | 申请、释放、续约、管理员强制回收 | 申请、释放、续约 |
| 注册 | 管理页注册/认领/下线 | 管理类工具（仅管理员 token 可见） |
| 不许做 | 直接改数据库状态 | 本地记录一份"我占了什么"当事实 |

# 第五部分：三个我认为最该先解决的

1. **MAC 稳定性验证（V2-01）** —— 整个身份方案押在"MAC 不变"上。这一步不做完，后面 DDL 的主键设计都是空的。现场 30 分钟能验完。
2. **SerialBridge 的租约校验（V2-03）** —— 如果不做，这套系统只是"登记表"，别人照样能直连串口绕过授权，"可管控"就是假的。
3. **MCP Server 落地（V2-11）** —— 这是使用入口：开发者配好 MCP 后，对着 AI 说"申请一台 QM102V 的板子做摄像头验证"就能占到资源，用完自动还。不做这一步，系统只是个后台台账，还得人去 Web 上点。
