## 1. 规模带来的三个硬前提

500–750 台、全部网络 ADB，意味着三件事不能靠人工兜：

1. **注册必须自动发现**，手工录 700 台不现实，且每次刷机后都可能要重录。
2. **ADB 授权必须统一**，不能每台板子第一次连接还要人去点"允许 USB 调试"。没屏幕的板子点了也点不到。
3. **IP 不能当身份**，700 台靠 DHCP 分配的地址随时会变。

---

## 2. 可用的身份信号（四类）

| 信号 | 采集方式 | 稳定性 | 说明 |
|---|---|---|---|
| **MAC** | `adb shell cat /sys/class/net/<if>/address` | A 型机稳定；Android WiFi 可能随机化 | 归一化为小写无分隔 |
| **SN** | `getprop ro.boot.serialno`（优先）/ `ro.serialno` / `ro.product.serial`；Linux 板读 `/proc/device-tree/serial-number`、`/etc/machine-id` | B 型机稳定；Android 10+ 上 `ro.serialno` 常为空，必须回退 `ro.boot.serialno` | |
| **硬件唯一 ID** | 芯片 efuse / chipid / `ro.boot.hardware.sku` 等厂商属性 | 最稳，但只有部分机型提供 | 有就优先用，是比 MAC 更硬的锚 |
| **固件版本 / 型号** | `getprop ro.build.display.id`、`ro.build.fingerprint`、`ro.product.model`、`/etc/os-release` | 刷机必变，同批设备还都一样 | 只能做弱信号，绝不能单独用 |
| **位置编号 + 资产标签** | 人工分配并贴标，格式如 `302-R2-05` | **永不随刷机变化，且位置唯一** | 唯一能兜住"全擦"的锚点 |
| **自建持久化资产文件**（建议新增） | 在 `/persist/asset_tag` 或 `/factory/asset_tag` 写入一行资产号，刷机脚本保留该分区 | 只要不擦 persist/factory 分区就不变 | 比 MAC 更可控，因为内容是你们自己写进去的 |

> **建议的第四条锚点**：给每个机型在镜像里加一个只读属性或 persist 文件，写入 `asset_tag`。这一条成本极低（刷机脚本加一行），收益是"哪怕 MAC 和 SN 全被擦，设备自己还能报出身份"。强烈建议在所有机型上做。

## 3. 分型策略（你说的三种，加一种兜底）

| 型 | 判定条件 | 主锚 | 辅锚 | 识别规则 |
|---|---|---|---|---|
| **A 型** | 有稳定 MAC（以太网、或 WiFi 未随机化） | MAC | SN、资产文件 | MAC 相同即同一台；SN 变了只更新声明 |
| **B 型** | MAC 不稳定或随机化，但有稳定 SN | SN | MAC、资产文件 | SN 相同即同一台 |
| **C 型** | 无稳定 MAC 也无稳定 SN | 自建资产文件 | ADB 接入地址、型号、固件指纹、物理位置 | 有资产文件则用它；没有则只能靠"位置 + 人工认领"，且每次刷机后需要人工确认 |
| **D 型（兜底）** | 连资产文件都没有、位置也记不清 | 无强锚 | 全部弱信号 | 进"待认领"，**不允许自动入池** |

**C 型的现实**：如果既没有 MAC/SN 也没有资产文件，那么每次全擦之后，系统没有任何自动手段能证明"这台还是原来那台"。这种情况下不要假装能自动识别，老老实实进人工认领队列 —— 700 台里 C 型占比应该压到最低，靠"加资产文件"把它转成 A/B 型。

## 4. 核心模型：`device_id` 永不变，标识是"可退役的声明"

### 4.1 为什么不把 MAC 直接做成主键

推演一次全擦：

```
第 1 天  设备在 3 号工位，MAC=AA:BB:01，SN=SN001 → 建记录 R1，历史占用 40 小时
第 30 天 全擦刷机，MAC 变成 AA:BB:99，SN 变成 SN999
        → 若 MAC 是主键：系统认为出现一台"新设备"，建 R2
        → 结果：R1 变成永远离线的僵尸记录，R2 没有历史，占用统计断裂
```

而"MAC 唯一"这个语义其实不需要它当主键 —— 用唯一索引就能保证，效果一样，但不会因为刷机把记录撕成两半。

### 4.2 三张表

```
device
  device_id        内部主键（如 D-0001），永不变
  display_name     QM102V-板3
  platform         型号/平台
  device_class     A / B / C / D（决定用哪套识别规则）
  location         物理位置（机架-层-位 / 工位号）   ← 人工锚
  asset_tag        资产标签（贴纸号 / persist 文件内容）
  access_mode      tcp（本方案全部为 tcp）
  adb_address      当前可用地址 ip:5555
  current_ip       最近一次 IP
  state            pending_identity / pending_probe / available / occupied / maintenance / offline
  maintainer       维护责任人
  last_seen_at

identity_claim        （标识声明：一台设备可以有多条，历史可退役）
  claim_id
  device_id
  claim_type        mac / sn / hwid / asset_file / asset_tag
  value_norm        归一化后的值
  first_seen / last_seen
  status            active / retired / conflict
  confidence

identity_event        （识别流水，只追加）
  event_id
  device_id?
  action            discovered / matched / new_pending / drifted / conflict / claimed
  signals           命中的信号与分值（JSON）
  actor             系统 / 管理员
  at
```

关键点：**同一台设备可以有多条 MAC 声明**（历史上被擦掉的那些），但任一时刻只有 `status=active` 的那条参与唯一性校验。

## 5. 匹配打分（自动/人工的分界线）

| 信号命中 | 分值 | 类型 |
|---|---|---|
| 资产文件 `asset_tag` 相同 | 100 | 强锚 |
| 硬件唯一 ID 相同 | 95 | 强锚 |
| MAC 相同（归一化后） | 90 | 强锚 |
| SN 相同 | 90 | 强锚 |
| 位置编号相同（且平台类型一致、该位置只有一台登记设备） | 85 | 强锚（人工保证、不随刷机变化） |
| 上次 IP 相同 | 40 | 弱 |
| ADB 接入地址（ip:port）相同 | 40 | 弱 |
| 型号 / 平台相同 | 25 | 弱 |
| 固件指纹相同 | 15 | 极弱（同批设备必然相同） |

决策规则：

| 条件 | 处理 |
|---|---|
| 任一强锚命中，且无冲突 | **自动认定同一台**，更新漂移字段，记 `drifted` 事件 |
| 无强锚，弱信号合计 ≥ 60 | 进"待确认"队列，管理员一键认领（不自动入池） |
| 无强锚，合计 < 60 | 新建 `pending_identity` 记录，等认领 |
| 强锚命中但已属于另一台活跃设备（如两个物理设备报同一 MAC） | 判 `conflict`，拒绝自动，告警 + 人工处理 |
| 强锚全部失效（全擦），但位置一致 | 提示"疑似同一台（位置匹配），可能已刷机" → 管理员确认后把旧声明退役、新声明挂到原 `device_id` |

**分值不是拍脑袋**：强锚之所以是 90+，是因为在这些机型上它们理论上唯一；弱信号之所以低，是因为同批设备的型号、固件必然相同，它只能用来"辅助排序候选"，不能用来"证明身份"。

## 6. 注册流程

```
① 发现（每 30 分钟，与巡检同一轮）
   网段扫描 5555 端口 → 得到活跃 IP 列表
        ↓
② 采集（对每个新 IP）
   adb connect ip:5555 → adb devices → 读 MAC / SN / 硬件ID / 型号 / 固件 / 资产文件
        ↓
③ 匹配（按 device_class 选锚点，算分）
        ↓
④ 分三种结果
   ├ 强锚命中 → 自动挂到已有 device_id，记漂移事件
   ├ 中分 → 待确认队列（Web 上一键认领）
   └ 低分 → 新建 pending_identity，等管理员命名/定位置/打资产标签
        ↓
⑤ 入池前健康探测（adb shell 可用才算通过）
        ↓
⑥ available，进入可申请池
```

**自动入池的最后一道闸**：`pending_identity` 和 `pending_probe` 状态的设备**不参与申请分配**。宁可少几台可用，也不能让一台身份不明的设备被 Agent 占走。

## 7. 标识漂移的五种真实场景

| 场景 | 现象 | 系统怎么处理 | 要不要人 |
|---|---|---|---|
| 刷了新镜像 | MAC/SN 没变，固件指纹变 | 强锚命中，自动认定，记固件变更事件 | 不要 |
| 擦了 SN，MAC 保留 | SN 变空或变默认值 | MAC 强锚命中，SN 声明退役 + 新声明 | 不要 |
| 全擦（MAC+SN 双变） | 两个强锚都失效 | 位置/资产文件命中 → 提示疑似同一台，需确认 | **要** |
| 换板（真换了硬件，位置不变） | 所有强锚都指向新硬件 | 位置命中 → 提示"疑似换板"，确认后把 asset_tag 迁到新硬件 | **要** |
| MAC 被克隆（两台报同一 MAC） | 一个 MAC 两个活跃实例 | 判 conflict，两台都暂停入池，告警 | **要** |

> 判定"要不要人"的标准很简单：**能不能靠强锚证明**。能证明就自动，不能就停下来等人 —— 自动猜错的代价（历史数据错挂、租约挂错设备）远高于让人点一下。

## 8. 网络 ADB 方案必须处理的四个坑

### 8.1 adbkey 未授权（**已由 data 区钩子覆盖，见 §12.2**）

网络 ADB 首次连接，设备会弹"允许调试吗"，没屏幕的板子根本点不了。现象是 `adb devices` 显示 `unauthorized`。

处理：
- 生成**团队统一 adbkey**，预置到设备 `/data/misc/adb/adb_keys`（或做进 system 镜像 / 开机脚本写入）。
- 所有扫描器、Agent、巡检器共用这把 key。
- 巡检探测到 `unauthorized` 时，不能判"设备坏"，应判"需重新授权"，并通知维护责任人。

### 8.2 刷机后 adbd 的 tcp 端口没开（**已由 data 区钩子覆盖，见 §12.2**）

默认 adbd 只走 USB。网络 ADB 需要 `setprop service.adb.tcp.port 5555` 并重启 adbd。
处理：把这条写进机型的开机脚本 / init.rc，让它**每次启动自动开**。否则每刷一次机，这台设备就从池子里消失一次。

### 8.3 DHCP 导致 IP 漂移

处理：
- 尽量在 DHCP 上做静态保留（但 MAC 变化后保留失效，所以别把保留当唯一手段）。
- 系统侧靠"30 分钟网段扫描"兜底重新发现。
- IP 只作弱信号，不作身份。

### 8.4 探测结果必须分级，不能只有"通/不通"

这是巡检和注册共用的关键设计：

| 级别 | 判定 | 含义 | 处理 |
|---|---|---|---|
| **L0** | ICMP 不通 | 断电 / 网线 / 关机 | 判 offline，通知维护责任人 |
| **L1** | ICMP 通，5555 端口不通 | adbd 没开或没起来（常见于刚刷完机） | 判 `adbd_down`，通知"需开 tcp 端口"，不算设备坏 |
| **L2** | 5555 通，`adb devices` 显示 `unauthorized` | adbkey 未授权 | 判 `unauthorized`，通知"需重新授权"，不算设备坏 |
| **L3** | `adb shell` 可执行 | 真正可用 | 健康，采集身份信息 |

只有 L3 才允许入池和参与分配。L0–L2 分别对应不同的维护动作，通知文案也不同 —— 这一条能省掉大量"板子是不是坏了"的无效排查。

## 9. 规模下的性能与并发

| 项 | 取值 | 说明 |
|---|---|---|
| 扫描周期 | 30 分钟（与巡检同轮） | 700 台 × 每轮 ≈ 全量网段扫 + 增量探测 |
| 单轮并发 | 10–20 路 | 网络 ADB 连接本身较重，别开 100 并发 |
| 单台探测超时 | adb 5s / ping 2s | 超时即降级，不阻塞整轮 |
| 身份采集频率 | 仅在"发现新设备"或"状态从 L0–L2 恢复到 L3"时采集 | 不要每轮都 `adb shell`，开销大 |
| 存储 | 每台每天 1–2 条巡检记录，700 台 ≈ 千级/天，一年 ≤ 50 万行 | SQLite 也可以，PostgreSQL 更稳 |
