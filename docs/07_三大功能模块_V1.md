| 项 | 内容 |

---

## 0. 先说清楚一件事

**三个域不是三个服务。** 它们共用同一个后端、同一套领域逻辑、同一个 PostgreSQL，只是对使用者呈现为三块：

- **A 设备申请** —— 使用者要资源时面对的那一块
- **B 设备注册** —— 新设备进系统时面对的那一块
- **C 设备管理** —— 管理员日常维护面对的那一块

这样切的好处：任何一个功能都能立刻回答"它属于谁的事"，评审和需求讨论时不会串。坏处：有些逻辑（比如状态机）会横跨三域，所以 §5 专门列了三条跨域硬连接。

## 1. 域 A：设备申请（面向使用者）

### A1　资源查询

| 项 | 内容 |
|---|---|
| 谁用 | Agent（`res_list_devices`）、人（Web 占用墙） |
| 输入 | 平台 / 机型 / 位置 / 指定设备号 / 需要多长时间 |
| 输出 | 可用列表（含 adb 地址、串口、最近一次健康检查时间）、占用列表（谁占的、到几点）、我的租约、我排第几 |
| 规则 | 只列 **L3 且未被独占** 的设备；可用性由服务端算一次，Web 与 MCP 结论必须一致；分页返回 |

### A2　申请与授予

| 项 | 内容 |
|---|---|
| 请求 | 目标（平台 + 数量，或指定 `device_id`）+ purpose + 期望时长 + 幂等键 |
| 流程 | 鉴权 → 配额校验（跨入口合计）→ 选设备 → 行锁 → 写租约 → 更新设备状态 → 发事件 → 返回 |
| 选设备策略 | 同平台优先 → 最近最少使用 → 同房间优先（减少跑动） |
| 无空闲时 | **不报错，转排队**，返回 ticket 与位次。这是本系统跟"直接拒绝"最大的差别 |
| 配额满时 | 拒绝，并告诉用户当前占用哪几台、什么时候到期 |

### A3　租约与续约

| 项 | 内容 |
|---|---|
| TTL | 默认 30 min |
| 续约 | `res_renew` 主动续约，单租约总时长有上限 |
| 宽限期 | 到期后 10 min 内仍可续约，超过即强制回收 |
| 为什么不做心跳 | Agent 在刷机、跑验证时不会持续调工具，纯心跳会误杀长任务 |
| 到期扫描 | worker 每 10s 扫一次，不靠请求触发 |

### A4　排队与唤醒

| 项 | 内容 |
|---|---|
| 队列类型 | 组队列（要"任意一台某平台"）、设备队列（指定某一台） |
| 排序 | priority 降序 → 入队时间升序（严格 FIFO，不插队） |
| 唤醒 | 释放时**只给队首发 offer**，资源转 RESERVED，60s 确认窗口 |
| 超时/拒收 | 顺延下一位，资源继续保持 RESERVED |
| 为什么不广播 | 广播会让多个 Agent 同时冲上来抢，形成惊群，反而都不确定自己拿到没有 |
| 查询 | `res_ticket` 查位次与预计等待；MCP 侧另有短阻塞等待（≤60s） |

### A5　释放与回收

| 项 | 内容 |
|---|---|
| 主动释放 | `res_release`，幂等，重复调用返回同一结果 |
| 超时回收 | 宽限期结束自动回收，写审计，通知原持有人 |
| 管理员收回 | 后台强制回收，**必须填原因** |
| 关键 | 回收与"唤醒下一位"在**同一事务**内完成，禁止分两步提交 |

## 2. 域 B：设备注册（面向新设备）

### B1　发现与接入

| 通道 | 说明 |
|---|---|
| 网段扫描 | worker 定期扫设备网段，发现 5555 开放的地址，进候选池 |
| 手工录入 | 管理员输入 IP / 位置编号 / 机型，系统主动去连一次 |
| 批量导入 | CSV 导入（适合整批新到货） |

三条通道最终都落到**同一个接入检查**：能不能 `adb connect` 成功，决定后续走哪条路。

### B2　身份采集

| 信号 | 来源 | 稳定性 |
|---|---|---|
| MAC | 网络接口 / `adb shell` 读 | 全擦会变 |
| SN | `ro.serialno` 等属性 | 部分机型稳定，部分会是默认值 |
| 硬件 ID | 芯片/板卡固有标识 | 相对稳定，不是都有 |
| 资产文件 | `/persist/asset_tag`（建议新增，刷机保留） | 最稳 |
| 位置编号 | 人工登记（房间 + 位置） | 不会因刷机变 |

**采集原则：采到什么记什么，缺项不阻塞注册。** 采集结果全部写 `identity_claim`，作为后续判定依据。

### B3　匹配与认定

| 打分 | 信号 |
|---|---|
| 100 | 资产文件 `/persist/asset_tag` |
| 95 | 硬件 ID |
| 90 | MAC |
| 90 | SN |
| 85 | 位置编号 |
| 40 / 40 / 25 / 15 | IP / 接入地址 / 型号 / 固件指纹（弱信号） |

| 决策 | 条件 | 结果 |
|---|---|---|
| 自动认定 | 强锚命中且唯一 | 直接绑定到台账里的那台 |
| 待确认 | 弱信号合计 ≥ 60 | 进 C3 人工确认队列 |
| 新建 | 无任何锚命中 | 建 `pending_identity` 记录，等人认领 |

**分型**：A 主锚 MAC / B 主锚 SN / C 主锚资产文件 + 位置 / D 无强锚（不允许自动入池）。

### B4　漂移与冲突

| 场景 | 判定 | 动作 |
|---|---|---|
| 换镜像 | 强锚不变，固件指纹变 | 自动更新版本信息，不改身份 |
| 擦 SN | SN 变，MAC 或资产文件不变 | 以未变的强锚为准，自动修复 |
| 全擦 | 强锚全变，位置编号命中 | 靠位置锚认回，需人工确认 |
| 换板 | 硬件 ID 变，位置不变 | 进冲突队列，人工迁移资产标签 |
| MAC 克隆 | 同 MAC 出现两个活跃实例 | 立即隔离两台，不允许自动授予 |

判定标准只有一句：**能不能靠强锚证明是同一台**。能证明就自动，不能就停下来等人。

### B5　入池与标注

| 项 | 规则 |
|---|---|
| 入池门槛 | 必须探测到 **L3（shell 可用）**；L0–L2 一律不入池 |
| 标注 | 机型、平台、系统版本、屏幕/LED 有无、串口数量 |
| 串口绑定 | 入池时绑定串口，后续随设备一起被独占 |
| 入池后 | 立即触发一次巡检，确认状态真实，避免"入了池但已经掉线" |

## 3. 域 C：设备管理（面向管理员）

### C1　设备档案与位置

- 字段：device_id、机型、平台、位置编号（如 `302-R2-05`）、IP、MAC、SN、资产标签、维护责任人
- 生命周期：`pending_identity` → `available` → `in_use` → `offline` / `retired`
- **上线前必须盘库一次**：贴标签、录位置、采 MAC/SN，否则位置锚不可信

### C2　状态与巡检

| 级别 | 含义 | 维护动作 |
|---|---|---|
| L0 | ICMP 不通 | 查电、查网线、查交换机 |
| L1 | 端口不通（ICMP 通） | 查 adbd 是否起来；结合历史判是否 data 被擦 |
| L2 | unauthorized | 重放 adb_keys |
| L3 | shell 可用 | 正常，允许入池 |

| 规则 | 取值 |
|---|---|
| 周期 | 15 或 30 min 可配，默认 30 |
| 判离线 | 连续 2 轮失败（单轮只标 suspect） |
| 疑似 data 被擦 | 原 L3 → L1 且连续 2 轮 |
| 恢复 | 恢复 L3 后下一轮自动回 `available` |
| 与租约的关系 | **掉线不改租约**，只标 degraded。不改，避免网络抖动误杀长任务 |

### C3　人工介入台

五个触发点，全部在这里处理：

| 触发 | 系统给什么 | 人做什么 |
|---|---|---|
| 待认领 | 候选设备 + 命中信号 + 置信度 | 命名、定位置、贴标签 |
| 疑似 data 被擦 | 恢复步骤 + 一键重试探测 | 重刷钩子、重放 keys |
| 强锚冲突 | 两台并排对比 + 最近活动时间 | 裁决哪台是真的 |
| 疑似换板 | 新旧差异清单 | 迁移资产标签 |
| 强制回收 | 占用时长 + purpose | 填原因并通知 |

**带屏/LED 辅助确认**：选中候选设备 → 点"点亮/显示编号" → 设备闪灯或屏幕显示 `D-0007 / 302-R2-05` → 现场人核对 → 点确认 → 写人工确认记录。这只是裁决依据，不进自动判定链。

### C4　通知与告警

| 事件 | 通知谁 |
|---|---|
| 掉线（连续 2 轮） | 维护责任人 + 当前占用人 |
| 疑似 data 被擦 | 维护责任人，附恢复指引 |
| 超时强制回收 | 原持有人 |
| 排队过久 | 队首，视阈值 |
| 恢复上线 | 责任人 |

同设备 2 小时内去重，避免轰炸。

### C5　审计、统计与权限

- 流水只追加，不可改：谁、什么时候、对哪台、做了什么、为什么
- 利用率按天聚合：可用时长 / 占用时长 / 离线时长
- CSV 导出
- 账号、token、资源组白名单、并发配额（默认 2 台）

## 4. 三个域的边界（一句话对照）

| 域 | 回答的问题 | 不属于它的事 |
|---|---|---|
| A 设备申请 | "我要用，怎么拿到、占多久、什么时候还" | 不负责设备从哪来、健不健康 |
| B 设备注册 | "这台设备是新来的，怎么证明它是谁" | 不负责分配，入池即交棒给 A |
| C 设备管理 | "现在整体什么状态、坏了谁修、谁用了多久" | 不直接改租约（除强制回收）、不自动改身份 |

## 5. 三条跨域硬连接（最容易被写歪的地方）

| # | 连接 | 违反的后果 |
|---|---|---|
| 1 | **B5 入池 → A 才可选**：A 只能从"L3 且 available"的池子里选 | 绕过入池门槛，L2 设备被授予，使用者连不上 |
| 2 | **C2 巡检只改健康，A3 租约只管时间**：掉线不回收 | 网络抖一下就把正在跑的长任务踢掉 |
| 3 | **C3 人工确认可改 B 的认定，但必须落 `identity_event`** | 人工改判不留痕，事后查不出为什么这台挂错了 |

## 7. 请你确认三点

1. **三个域是否够**：还是需要把"系统设置（账号、token、参数配置）"单独拎出去？我倾向放在 C5，因为它跟设备无关，但量很小，单独成域会让框图显得空。
2. **申请的粒度**：是只支持"给我一台某平台的"，还是也要支持"我要 3 台"和"指定某一台"？后者会让配额与排队规则复杂一档。
3. **C 域是否要再拆**：管理里的"日常维护（巡检、告警）"和"配置（账号、配额）"职责差别较大，如果以后要分给不同人，可能拆成 C 维护 / D 配置两组。

## 8. 下一步

三域确认后，按域出详细设计：

1. **A 域**先出 —— 它是使用者直接感知的部分，接口一改所有人都有感觉
2. **B 域**其次 —— 决定数据模型，但可以并行
3. **C 域**最后 —— 依赖前两者的状态与事件
