| 项 | 内容 |

## 修订点（相对 V1）

| 项 | V1 | V1.1 |

## 1. 主流程

| 步 | 谁做 | 做什么 |
|---|---|---|
| 1 | 管理员 | 维护名单：邮箱、姓名、资源组、每人配额、有效期（默认 90 天） |
| 2 | 管理员 | 一键批量生成：**每人 3 条凭据**，连同领取口令 |
| 3 | 系统 | 发邮件：领取链接 + 一次性口令（10 分钟有效）+ 填写说明 |
| 4 | 本人 | 点**一次性免登录链接**（10 分钟有效，点开即显示 3 条 token，页面不重复展示）→ 分别给不同的 Agent |
| 5 | Agent | 首次调用时自动带上自己的名字，记录一次首见信息 |
| 6 | — | 之后直接申请，无需审批 |

**注意**：全流程中**只有管理员登录 Web**，普通人不需要登录任何界面。

**关键一点**：3 条凭据是**并列**的，没有"主/备"之分。人把哪条给哪个 Agent 用，系统不强制；但每条凭据都会记录"第一次被谁用了"（Agent 名 + 来源 IP），从此固定。

---

## 2. 代价盘点（V1 说三个，现在只剩一个半）

### 2.1 代价一：名单即授权，没有第二道审批（**仍然存在**）

进名单就等于有权限，没有第二道审批。风险：离职未摘、外包到期未删、名单录错人。

兜底（必须做进系统）：

1. 离职一键摘除：吊销该人全部凭据 + 释放全部租约 + 队列条目作废
2. 季度核对：系统生成"近 30 天未调用"清单
3. **90 天到期强制失效**（你说的这条）
4. 名单变更留流水：谁加的、谁摘的、什么时候

这是三个代价里唯一必须靠"制度 + 系统"共同兜的。

### 2.2 代价二：Agent 粒度 —— **你说得对，这个代价基本不存在**

我原来的担心是"token 按人发，分不清是哪个 Agent"。但把下面三点叠起来，它就不成立了：

| 因素 | 效果 |
|---|---|
| **token 绑人** | 设备被谁占，**100% 可靠**。这是追责的核心，跟 Agent 名字无关 |
| **每人 3 条凭据** | 三个 Agent 天然分槽，三条凭据的占用记录本身就是分开的 |
| **名字自动带出** | 展示层也有名字了，不用人填 |

所以准确的说法是：**"谁在用"始终确定（靠 token），"用什么 Agent"是附赠信息（靠自动取 + 可覆盖）**。

补一条技术事实：MCP 协议 `initialize` 请求里本来就带 `clientInfo`（name + version），Cursor 会填 "Cursor"、Claude Desktop 填 "claude-ai"、CodeBuddy 也会填。**所以 Agent 名是零成本自动获得的，不需要让人填。**

只在两种情况下需要人介入改：
- 各家客户端填的名字不统一（有的填全名、有的填包名）→ 人在 Web 上改一次
- 同一个 token 被两个 Agent 共用 → 系统取"第一次调用"的那个名字并固定，避免来回变

---

### 2.3 代价三：邮件是明文通道（**仍然存在，形态待你定**）

邮件会归档、被搜索、被转发、被规则抄送。token 明文进邮件 = 进了一个长期可检索的存储。

两个选项，需要你选：

| 方案 | 邮件里放什么 | 体验 | 风险 |
|---|---|---|---|
| **A（推荐）** | 领取链接 + 10 分钟一次性口令 | 多一次点击、一次登录 | 邮件泄露拿不到 token |
| B | 正文直接贴 3 个 token | 复制即用，最省事 | token 长期躺在邮箱里，建议有效期缩到 30 天 |

## 3. 到期与续期（你要求支持）

| 项 | 规则 |
|---|---|
| 默认有效期 | 90 天 |
| 到期行为 | **强制失效**，Agent 调用返回 401，看板把该凭据标"已过期" |
| 提醒 | 到期前 7 / 3 / 1 天，发邮件 + Web 顶部提示 |
| 单人续期 | Web 点一下，延长 90 天 |
| 批量续期 | 按名单全量或按筛选批量延长，不用逐个点 |
| **续期是否换 token** | **不换**。只延长 `expires_at`，Agent 侧配置不动 |

**为什么续期不换 token**：一旦换，所有人的 MCP 配置都得重新改一遍，等于把"免人工分发"的收益全吐回去。若某天出于安全要求必须轮换，那也应该做成"新旧并存 30 天 + 提示替换"，而不是直接断。

**过期未续的人**不进"自动续期"，需要管理员点一下，避免"人早就不用了但一直有效"。

---

## 4. 激活：只做一次记录，之后只认 token

| 项 | 规则 |
|---|---|
| 激活条件 | 首次成功调用（任一工具） |
| 激活时写什么 | 只记一次：Agent 名（取 MCP `clientInfo`，取不到就留空）、来源 IP、首次时间 |
| 激活后 | 不再更新、不再校验，不看名字、不看来源 |
| 换电脑 / 重装 / 换 Agent | 直接继续用同一条 token，不需要任何操作 |
| 每次调用校验 | 只有四条：① token 存在且未吊销 ② 未过期 ③ 人的配额未超 ④ 设备可用 |

**一句话**：激活是一次打点，不是上锁。首见信息只进审计，不参与任何判断。

补偿只有一条：token 泄露时随时在 Web 吊销这一条，影响面限于它自己，不动别人的。

看板与审计展示：

| 位置 | 显示 |
|---|---|
| 占用墙 | 「张三 · Cursor」（有记录时）/「张三」（无记录时） |
| 审计明细 | 人 + 凭据编号 + 首见 Agent 名 + 首见 IP |
| 统计 | 按人聚合（配额是人的） |

---

## 5. 名单与凭据的关系

```
名单（人 + 邮箱 + 资源组 + 配额 + 有效期）
   └→ 批次发放 → 每人 3 条凭据（credential × 3）
                    └→ 每条独立：独立到期、独立吊销、独立绑定 Agent 名
```

一人的 3 条凭据**共享同一个人的配额**（默认 2 台），不会因为"有 3 条凭据"就变成 6 台。这条必须写死，否则 3 条凭据就是 3 倍额度。

---

## 6. 数据表

```sql
roster              -- 名单
  id, email, name, employee_no, resource_group, quota,
  effective_from, effective_to, status(待发|已发|已领|已过期|已摘除), note

agent_credential    -- 凭据（每人 3 条）
  id, principal_id, roster_id, seq(1..3),
  token_hash, token_prefix, scope, issue_channel(mail|web|self),
  claim_code, claim_expires_at, claimed_at,
  agent_label, agent_label_source(client_info|manual|ua),
  source_ip, first_seen_at,
  expires_at, revoked_at, last_used_at, last_lease_at

credential_event    -- 凭据流水
  id, credential_id, action(issue|claim|bind|renew|revoke|expire), operator, at
```

配额仍在 `principal` 层，**不在凭据层**。

## 9. 三个硬缺口（不补跑不通）

### G1　领取页身份校验 —— **已按你的口径收敛**

**你的口径**：只有管理员登录 Web，个人不登录、只通过 MCP 调服务。

据此：

| 项 | 定论 |
|---|---|
| 登录的人 | 只有管理员（1–2 个账号） |
| 个人的自助界面 | **不做**。不发"我的占用"、不发"我的凭据"页面 |
| 领取方式 | 邮件给**一次性免登录链接**：10 分钟有效，点开即显示 3 条 token，页面不重复展示 |
| 为什么不用"正文直接贴 token" | 链接 10 分钟就死，正文会永远躺在邮箱归档里；不登录也能做到这一点 |
| 需要本人的操作 | 只有两步：点链接复制 token、贴进 MCP 配置。其它一概不做 |
| 管理员的替代动作 | 改 Agent 名、续期、吊销、补发，全部由管理员在 Web 上做 |

**剩下唯一要定的**：管理员账号怎么建 —— 一期本地账号 + 密码（1–2 个）最省，二期再接 SSO。

### G2　"人"的唯一键 —— **已定：邮箱**

**你的口径**：参与人员固定，一人一个邮箱，不存在一人多邮箱。据此确定：

| 项 | 定论 |
|---|---|
| principal 唯一键 | **邮箱**（`roster.email` 建唯一索引） |
| 重复导入 | 按邮箱 upsert 合并，**不新建**（实现层行为，不需要人决策） |
| 配额 / 租约 / 凭据 | 全部挂邮箱 |
| 工号 | 只做展示字段，**不做唯一键**，省掉一套映射维护 |
| 外包 / 临时人员 | 同样用邮箱登记，靠"失效日期"控制，到期自动吊销 |

这样也顺带简化了 G1：**收 token 的地址和登录校验的地址是同一个**，用"邮箱 + 一次性验证码"登录最自然。

### G3　摘除时租约怎么处理

**问题**：写"摘人 = 吊销凭据 + 释放租约"，但没说是什么时候放。人在被摘的当下可能正占着 2 台设备跑验证。

| 选择 | 后果 |
|---|---|
| 立即回收 | 打断正在进行的验证；但安全上干净 |
| 到期自然结束 | 最多多占 30 分钟；窗口内他还能续约吗？能就变成长期滞留 |

**建议**：**立即回收**，同时给占用人发一条"你的凭据已被吊销，设备已回收"的通知。理由：已不在名单的人继续持有资源，本身就是风险；真要收尾，应该先让他自己释放，再摘名单。

## 10. 五个次要缺口（不影响跑通，但会影响体验）

| # | 缺口 | 建议 |
|---|---|---|
| G4 | 邮件发送失败 / 退信没有状态 | 台账加一个"发送失败"视图，可一键重发 |
| G5 | 3 条全部激活后还想加第 4 个 Agent | 吊销一条再补发（不用等邮件，Web 直接给新 token） |
| G6 | 过期很久的凭据是否还能续期 | 过期超过 30 天只能重新发放，不允许"复活"，避免僵尸凭据 |
| G7 | 服务账号（CI 机器人）没纳入名单模型 | 名单加 `type=service`，配额单列，不占某个人的额度 |
| G8 | 邮件链接可达性（人在家 / 手机看邮件） | 链接域名要能从内网访问；另提供"手动输入口令"的入口兜底 |
