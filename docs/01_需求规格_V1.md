## 1. 背景与要解决的问题

当前测试资源（真机、开发板、串口）靠人工登记与口头协调。接入 AI Agent 后暴露出四类问题：

1. **占用不可见**：谁在用、用了多久、还要用多久，没有统一视图。
2. **占用不可控**：Agent 进程崩了、任务结束了没人释放，资源被长期锁死。
3. **抢占冲突**：两个 Agent（或两个人）同时 `adb connect` 同一台设备、同时打开同一串口，互相打断。
4. **排队靠人**：资源释放后没有人知道，只能靠群里喊。

本系统的定位：**把 ADB 设备与串口变成"可申请、可排队、可回收、可审计"的资源**，用一套 Agent API + 一个 Web 控制台统一管理。

### 成功判据（可量化，可验收）

- 任一时刻，同一 (设备, 串口) 只存在一个有效租约，冲突事件为 0。
- Agent 异常退出后，资源在 `心跳超时 + 回收延迟`（默认 90s）内自动回到资源池。
- 资源释放到队首拿到资源的中位时间 ≤ 确认窗口（默认 60s）。
- 能回答"过去 7 天每台设备被占用多少小时、闲置多少小时、被谁占用"。
- 全量占用流水可追溯：谁、何时、申请了什么、怎么结束的（主动释放 / 超时 / 强制回收）。

### 1.1 定位澄清：这是"服务"，不是"门禁"（2026-11-07 追加）

**使用者就是 Agent。** Agent 按 MCP / Skill 的规则走：先 `res_apply` 拿租约，拿到 `adb_address` 再去连，用完 `res_release`。

**本系统不追求"拦住绕过的人"**，有两个理由：

1. **技术上做不到**：设备是网络 ADB（tcp 5555），局域网内任何人只要能路由到设备就能 `adb connect`，本系统无法阻断——除非做网络隔离，而这一期已经明确不做。
2. **也没必要**：如果申请路径足够顺手，绕过反而是更费事的选择。

因此三条设计取向：

| # | 取向 | 具体做法 |
|---|---|---|
| 1 | **便利即合规** | `res_apply` 一次就返回 `adb_address` + 串口，Agent 不必自己扫网段、猜 IP。申请比绕过省事，自然就不绕 |
| 2 | **规则写在约定里** | MCP 工具描述与 Skill 文档里写死"先 apply 再连、用完 release"。这是约定，不是强制 |
| 3 | **统计口径要诚实** | 利用率、占用时长只能统计"经中心申请的部分"。有人直接 `adb connect`，系统看不见，报表里必须注明口径 |

**最轻一层兜底（可选，先出策略不做实现）**：巡检时若某设备"没有任何有效租约"却存在活跃 ADB 连接（`adb shell cat /proc/net/tcp` 中 5555 处于 ESTABLISHED），标一条"疑似未申请占用"，只提示、不处理。这样管理员至少能看到"有人在绕"。

**一句话**：绕过是个别人的问题，不是系统要解决的问题。系统要做的是让"按规矩来"这件事足够省事。

### 1.2 入口原则：Agent 只有一个门，就是 MCP（2026-11-07 追加）

| 使用者 | 入口 | 鉴权方式 |
|---|---|---|
| **Agent** | **MCP Server（唯一入口）** | Bearer token（`rr_...`） |
| **人** | **只有管理员登录 Web 控制台** | 管理员账号 |

整个服务对 Agent 来说就是一个 MCP：连上来、带 token、调工具，其他什么都没有。

**普通人（凭据持有人）不登录任何界面**：拿到 token 后直接配进 MCP 即可用。看板、名单、发凭据、续期、吊销、强制回收，全部由管理员在 Web 上操作。

这条带来的后果要说清：**个人没有任何自助入口**。换 Agent、token 泄露、配额不够，都得找管理员。在"人员固定、管理员就一两个人"的规模下，这是合理取舍——但也意味着管理员的日常动作要足够省事（批量发、批量续、一键摘）。

**为什么不再给 Agent 开一套 HTTP API**：开两个门就有两套鉴权、两套幂等、两套错误码。Agent 会挑顺手的那个用，行为对不齐；"两端结论一致"只能靠人守，守不住。

**三条硬约束**：

1. **Agent 需要的任何能力，都必须以 MCP 工具形式存在。** 禁止出现"只有 HTTP 才有的功能"——那等于逼 Agent 去绕。
2. **MCP Server 是团队共享单实例**，走 streamable HTTP 传输。不允许每人本地跑一套 stdio（那样全局状态不唯一，冲突检测直接失效）。
3. **注册是唯一例外**：首次拿 token 不能走 MCP（MCP 连接本身就要 token），走 09 文档的邮件 / 领取页。

**token 怎么配进客户端**（两种都支持）：

```
# 优先：header
Authorization: Bearer rr_3f9c2a11_xxxxxxxx

# 兼容：URL 参数（不少客户端只允许填 URL）
https://res.corp.com/mcp?t=rr_3f9c2a11_xxxxxxxx
```

两种方式日志里都要脱敏（`Bearer` 与 `t=` 都打码）。

## 2. 范围界定

### 2.1 在范围内（V1 必做）

- 资源注册与台账维护（手工登记 + CSV 批量导入）
- 资源的可用 / 占用 / 维修 / 下线状态管理
- Agent 通过 API 申请、续约、释放
- 人工（内部同事、外部客户）通过 Web 申请、排队、释放
- 租约机制：TTL + 心跳 + 超时自动回收
- 排队队列：FIFO + 预留确认窗口，释放后主动唤醒
- Web 实时看板：占用墙、队列、我的占用
- 审计日志与导出
- 设备巡检（30 分钟一轮）与掉线维护通知

### 2.2 明确不做（非目标）

- 计费、结算、跨公司对账
- CI/CD 流水线调度编排（可作为下游调用方，本系统不承担调度）
- 自动化测试脚本编排与测试结果管理
- 串口数据内容代理转发（见 7.3 的取舍说明）
- 移动端 App、复杂自定义 RBAC 策略引擎
- 资源使用时长计量的"公平算法"（V1 只做优先级 + FIFO）

## 3. 角色与权限

| 角色 | 定义 | 关键能力 | 限制 |
|---|---|---|---|
| 资源管理员 Admin | 资源池责任人 | 注册/编辑/下线资源、批量导入、健康探测、强制回收、调优先级、拉黑 holder、看全部数据 | — |
| 内部申请者 User | 内部同事 / 内部 Agent 持有人 | Web 申请、排队、续约、释放、查看自己的占用 | 只能申请被授权的资源组 |
| Agent 申请者 Agent | 自动化程序，凭 token 身份 | 调 API 申请、心跳续约、释放、订阅事件 | token 绑定资源组白名单 + 并发配额 |
| 外部客户 Customer | 被邀请的外部使用方 | Web 申请、排队、释放、查看自己的占用 | 只看自己可见的资源组，无管理页 |
| 观察者 Viewer（待定） | 组长 / 项目负责人 | 只读看板与报表 | 不可操作 |

**要点**：Agent 不是"无身份的系统调用"，每个 Agent 都是一个可识别的 holder（有 token、有配额、可被拉黑）。这是后续排查"到底是谁把设备占死"的前提。

## 4. 资源模型

### 4.1 设备（Device）

| 字段 | 说明 | 备注 |
|---|---|---|
| device_id | 系统内主键，创建后不变 | 不是 adb 序列号的镜像，见 4.3 |
| display_name | 展示名，如"QM102V-板3" | 看板上显示 |
| sn | 硬件序列号 | 用于对账，不保证唯一 |
| platform | 平台/型号，如 QM102V / BES2800 | 用于分组与筛选 |
| access_mode | usb / tcp | tcp 时需 adb_address |
| adb_address | `usb serial` 或 `host:port` | Agent 拿到后直接 adb connect |
| group | 所属资源组/项目 | 排队以组为单位，见第 6 节 |
| state | available / occupied / reserved / maintenance / offline | |
| share_policy | exclusive（默认）/ shared + max_holders | |
| ports | 关联的串口列表 | 见 4.2 |
| tags | 用途、系统版本等标签 | 自由筛选 |
| probe | 健康探测方式 + 最近一次结果与时间 | 二期做自动上下线 |

### 4.2 串口（Port）

| 字段 | 说明 |
|---|---|
| port_id | 系统内主键 |
| device_id | 强绑定的宿主设备；允许存在"游离串口"（device_id 为空） |
| physical_ref | 物理位置标识，如 SerialBridge 的 device_id / Windows COM11 / 板端 `/dev/ttyUSB0` |
| default_baud | 默认波特率，Agent 可覆盖 |
| state | available / occupied / maintenance / offline |
| access_credential | 只记录"由哪套凭证体系授权"，不存明文 |

### 4.3 身份稳定性（必须解决的一条）

直接用 `adb devices` 的序列号做资源主键会出问题：重新插拔、换 USB 口、板子换镜像后序列号可能变化，台账会出现"每次重插多一条记录"，历史占用数据断裂。

**规则**：`device_id` 由 `sn + 物理端口路径`（或与 SerialBridge 的 device_id 交叉绑定）生成并持久化。设备重新上线时按此匹配回原记录，不新建。无法匹配时进入"待认领"状态，由管理员人工挂接，而不是静默新建。

## 5. 核心设计：租约（Lease），而不是"借还登记"

这是整个系统的设计中枢。AI Agent 不可能"记得还"，所以不能用被动登记模型。

### 5.1 租约内容

```
lease_id, device_id, port_ids[], holder（人或 agent）, purpose（可选，任务号/备注）,
granted_at, ttl, expires_at, last_heartbeat_at, state, idempotency_key
```

### 5.2 生命周期与状态机

```
IDLE
  └─ apply → QUEUED（无空闲资源）或多资源时 → RESERVED
RESERVED（给队列 offer，确认窗口内）
  └─ confirm → GRANTED ；超时/拒绝 → RELEASED（顺延下一位）
GRANTED / ACTIVE
  ├─ heartbeat（每 30s）→ 延长 expires_at
  ├─ 续约失败 1 次 → SUSPECT（仅告警，不回收）
  ├─ 心跳中断超 3 个周期 → EXPIRED（强制回收，唤醒队列）
  ├─ holder 调 release → RELEASED（立即回收，唤醒队列）
  └─ Admin force_release → FORCED（记审计，可拉黑 holder）
```

### 5.3 默认参数（待定，建议值）

| 参数 | 建议值 | 理由 |
|---|---|---|
| 默认 TTL | 30 min | 单板调试、单次刷机验证的量级 |
| 心跳间隔 | 30 s | 与 TTL 比值 1:60，容忍偶发网络抖动 |
| 判 SUSPECT | 丢 1 次心跳 | 只提示，不打断 |
| 判 EXPIRED 回收 | 丢 3 次心跳（≈90s） | 兼顾 Agent 短时卡顿与回收及时性 |
| 调度器扫描周期 | 10 s | 保证超期被及时发现 |
| 队列预留确认窗口 | 60 s | 够 Agent 重新连一次 WS、够人点一下 |
| 单 holder 并发占用上限 | 3 台（可配） | 防止一个 Agent 把池子扫光 |

## 6. 排队机制

### 6.1 排队粒度（待定，建议）

建议 **按"资源组"排队为主 + 支持指定 device_id 排队**：

- 按组排队：Agent 说"我要一台 QM102V 的板子"，调度时从组内挑一台空闲的给。好处是某台设备坏了不会卡死整条队列。
- 指定设备排队：用户说"我就要板3（已经刷好我要的镜像）"，进入该设备的独立队列。

### 6.2 优先级

`priority`：0 普通 / 1 高优 / 2 紧急，由管理员按项目或 holder 设置。排序规则：**priority 降序 → 入队时间升序**。V1 不做抢占（高优先级不能踢掉正在使用的租约），只影响排队顺序。

### 6.3 防惊群（关键细节）

资源释放时**不能广播"有空闲了，先到先得"**，否则多个 Agent 同时冲上来抢，谁手快谁得，用户体验极差且难以审计。

规则：
1. 释放后，调度器只向队首发出 `offer`，租约进入 `RESERVED`。
2. 队首在 60s 内 `confirm` 则转 `GRANTED`；超时未确认或显式拒收 → 顺延下一位，同时给被顺延者一条"本轮未抢到，仍排第 N 位"的通知。
3. `RESERVED` 期间该资源对其他任何人不可见为空闲（避免被抢）。

### 6.4 排队者主动退出

队首/队中可随时 `cancel`；支持设置"最长可等时间"，超时自动出队并通知，避免僵尸排队。

## 7. 通知与对接

### 7.1 事件

`resource.available` / `lease.granted` / `lease.offer`（带确认窗口倒计时）/ `lease.expiring`（剩余 20% TTL）/ `lease.revoked`（超时或强制回收）/ `queue.position_changed`

### 7.2 推送通道

- **WebSocket**：Web 看板与 Agent 长连接（实时性 ≤2s）
- **Webhook**：可配到企业微信 / 飞书 / Agent 平台，用于"资源已可用"这类需要人介入的提醒
- **轮询接口**：兜底，供不能长连接的 Agent

### 7.3 与现有通道的关系（待定，建议）

本系统只做**授权与租约**，不重复造"通道代理"：

- 串口读写 → 复用 SerialBridge（`sb_agent_*` token 授权），本系统负责"发凭证 + 记租约"，不参与字节流。
- ADB 连接 → 复用现有 adb 网关 / `adb connect host:port`，本系统只下发地址与授权。

前提：串口服务端要能接受"携带本次租约 ID 的连接"或按 token 限定可访问的 device_id，否则无法阻止绕过本系统直连串口。**这是本方案唯一有外部依赖的地方，需要确认。**

若做不到，"多机跨网络统一入口"才需要在本系统内做一层代理（成本显著上升，V1 不建议）。

## 9. Agent API 草案

```
POST /api/v1/leases/apply        # 申请（组 or 指定设备），带 Idempotency-Key
POST /api/v1/leases/{id}/confirm # 确认 offer（RESERVED → GRANTED）
POST /api/v1/leases/{id}/heartbeat
POST /api/v1/leases/{id}/release # body 可带 reason
GET  /api/v1/leases/current      # 我当前持有的
GET  /api/v1/resources?group=&state=
GET  /api/v1/queue/{group}
GET  /api/v1/events              # SSE / WS
```

认证：`Authorization: Bearer <agent_token>`，token 绑定 holder 身份 + 资源组白名单 + 并发配额。

**三个必须做对的细节**：

1. **幂等**：`apply` 带 `Idempotency-Key`，网络重试不会重复占号（AI Agent 重试是常态）。
2. **返回即用**：授予响应里必须直接给出 `adb_address` 和 `ports[].physical_ref`，Agent 不需要二次查询。
3. **release 要幂等**：重复 release 返回 200 而不是 404，避免 Agent 清理逻辑反复报错。

## 10. 硬规则（一致性与冲突）

| 规则 | 内容 |
|---|---|
| 唯一性 | 同一 device 的 exclusive 租约全局唯一；shared 按 max_holders 计数 |
| 串口从属 | 默认 grant 设备时一并锁定其全部串口（exclusive），避免"我拿设备、你拿串口"互相破坏；可按资源组配置为可放开 |
| 幂等 | apply / release 都按 idempotency-key 去重 |
| 并发 | 队列序号原子分配；授予走行锁或乐观锁，禁止两个请求同时拿到最后一台 |
| 兜底回收 | 独立调度器每 10s 扫过期租约，不依赖 holder 主动释放 |
| 强制回收告知 | force_release 必须通知原 holder，并记入审计（原因、操作人） |
| 断连不提权 | holder 连接断开不等于释放，只有心跳超时或显式 release 才释放 |

|---|---|---|---|
| 1 | 排队粒度 | 单设备排队 / 组排队 / 两者都要 | 两者都要，组排队为主 |
| 2 | 串口是否随设备自动独占 | 强制独占 / 可配置 / 独立申请 | 默认强制独占，按组可配 |
| 3 | 通道代理 | 自建代理 / 复用 SerialBridge + adb 网关 | 复用，本系统只做授权与租约 |
| 4 | 参数默认值 | — | TTL 30min / 心跳 30s / 回收 90s / 窗口 60s / 并发 3 |
| 5 | 人是否也走租约模型 | 人走同一套 / 人另走一套 | 走同一套，统一状态机与看板 |
| 6 | 客户范围 | 仅内部 / 外部客户也要账号隔离 | 需明确：外部客户是否只看自己可见资源组 |
| 7 | 是否需要账号体系 | 复用内部 SSO / 自建账号+邀请码 | 一期自建（账号+邀请码），二期再考虑 SSO |
| 8 | 优先级是否可抢占 | 只排序 / 可抢占低优先级 | 一期只排序，不抢占（实现简单、风险低） |

## 13. 验收标准（可测）

1. 两个 Agent 并发申请最后 1 台设备：恰好 1 个 `GRANTED`，另 1 个进入队列，无重复授予。
2. Agent 强杀进程后，资源在 90s 内回到 `available`，队列首位收到 `offer`。
3. 队首在 60s 内未确认，资源自动顺延给下一位，两位都收到对应通知。
4. 同一台设备的串口不会被第二个 holder 拿到（在默认独占策略下）。
5. 设备重插（USB 口不变）后，台账未新增记录，历史占用可连续查询。
6. 看板从"资源被释放"到"显示空闲"的延迟 ≤ 2s。
7. 任意一条租约都能导出完整流水：holder、申请时间、结束方式、结束时间、操作人。
8. 重复提交同一 `Idempotency-Key` 的 apply，返回同一 lease_id，不产生第二条记录。

## 14. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 串口服务端不支持按租约授权 | 无法阻止绕过系统直连串口 | 一期先做"约定 + 审计"，二期推动 SerialBridge 支持租约 ID 校验 |
| adb 序列号漂移 | 台账碎片化 | 采 4.3 的组合键 + 待认领机制 |
| Agent 端不实现心跳 | 租约频繁超时回收 | 提供 SDK/CLI 封装三接口；文档里明确"不心跳 = 会被回收" |
| 客户方并发不可控 | 资源被外部长期占用 | 外部客户单独配额 + 最长持有时长上限 |
| 强制回收引发的争议 | 责任不清 | force_release 强制填原因 + 通知原 holder + 落审计 |
