# PT10 设计评审：设备页信息架构整合（运行态 / 配置态）

> 任务：PT10｜分支 `feat/capabilities`｜VERSION `0.54.2`｜**只落设计，不改业务代码**  
> 现场设备页：`#/device/dev_997b70adae`  
> 基线：[`docs/PT9-设备能力卡片-语义修正与重排-设计评审.md`](./PT9-设备能力卡片-语义修正与重排-设计评审.md)（**本轮不修改 PT9**；P1–P4 结论沿用，本轮在其之上做整页 IA）  
> 用户新增反馈：A「电源绑定」与能力电源卡重叠且混入配置噪音；B 底部「串口」表与能力串口卡重复，且混入 `role=power`。

## 0. 目标与范围

| 编号 | 问题 | 一句话目标 |
|------|------|------------|
| **IA1** | 电源通道在能力卡 / 电源绑定表 / 串口表三处呈现 | 运行态只在能力·电源卡出现一次；配置字段进 admin 配置面 |
| **IA2** | 开/关/重启两套按钮 | **同一动作只保留一个入口**（推荐：能力卡） |
| **IA3** | 串口在能力卡 + 底部表重复；表内含 power | 运行态只在能力·串口卡；health/holder 并入卡内；底部表删除或折叠为端口明细 |
| **IA4** | 配置字段（位置/来源/label/slot/节点选择器）污染日常运行视图 | operate / configure 分层；非 admin 不看节点选择与可绑定通道表 |

**非目标**：PowerRes 协议改版、独立 Vue Router 拆分、DB schema、本轮落地业务代码、改 MCP 租约语义。  
**与 PT9 关系**：PT9 修能力模型与卡内布局（P1 假 serial.io、P2 只读、P3 ADB、P4 三卡一排）。PT10 在设备页**整页**消重：能力区 +「电源绑定」卡 +「串口」表 + 头栏入口。实现顺序建议：**先 PT9 P1（后端）再 PT10 前端 IA**，否则串口表/能力卡仍可能出幽灵 power 行。

### 1.3 加载链路（为何难「一次查询」）

设备页刷新并行拉三套数据（`App.vue` L2641–2646）：

| 调用 | 用途 |
|------|------|
| `GET /api/devices/{id}` | 指纹 + `serial_openable` / `serial_ports` |
| `GET /api/devices/{id}/capabilities` | 能力卡 items |
| `GET /api/devices/{id}/serial` | 底部串口表 + busy + 推断电源节点 |
| `GET /api/powerres/overview` + 每节点 `bindings` 过滤本机 | 「已绑定到本机」 |
| `GET /api/powerres/inventory?node_id=` | 「可绑定通道」 |

列表页另有 `serial.power_n` 等 flags（`router.py` L324–338），**详情页未用**；详情靠 bindings 计数。

### 1.4 根因一句话

设备页把 **Phase 1 能力发现（operate）**、**PowerRes 绑定闭环（configure，PT4a）**、**serial.caps 原始端口表（debug/AI）** 三套面叠在同一滚动页，且未按角色折叠；再叠加 PT9 P1（power 误产 serial.io），形成「同一通道三处、同一开关两套」。

## 2. 目标信息架构（单一来源）

### 2.1 分层原则

| 层 | 受众 | 放什么 | 不放什么 |
|----|------|--------|----------|
| **operate（运行态）** | 所有登录用户（动作仍受租约/admin 闸） | 能力区三卡一排（沿用 PT9 §4）：状态、端点摘要、health/holder、开/关/重启、串口控制台、ADB | 节点选择器、可绑定通道表、位置/来源/driver、解绑/抢绑 |
| **configure（配置态）** | **仅 admin**（默认折叠或迁 CtrlRes） | 节点归属、inventory 候选、绑定/解绑、slot/label/enabled、location/restart_hold_ms 编辑入口 | 重复的开/关/重启按钮 |
| **摘要** | 所有人 | 右栏：健康级别、已绑电源路数（只读 tag） | 操作按钮 |

**单一来源规则（硬）**：

1. 电源通道身份与开关：**只在能力·电源卡**。  
2. 绑定关系维护：**只在 configure 面**。  
3. 串口 IO 身份 + 控制台 + health/holder：**只在能力·串口卡**（多口则多卡或卡内列表）。  
4. `role=power` **永不**出现在串口运行列表（后端 PT9 P1 + 前端表过滤双保险）。  
5. 配置字段（location / source·driver·com / slot / label / restart_hold_ms）：卡内「详情」折叠或仅 configure 面。

### 2.2 能力卡内字段建议（去重后）

**电源卡（operate）**

| 行 | 内容 | 来源 |
|----|------|------|
| 标题 | label（如 bull1 CH1）+ status tag | capabilities item |
| 端点 | endpoint 单行 | `transport` / `binding` |
| 摘要 tag | `CH{n}` · `power_dev`（可选） | `binding.power_dev` / `channel`（`_powerres_binding_view` L849–864） |
| 动作 | [开][关][重启] + hold_ms + 补偿开 | **唯一入口** |
| 详情（折叠） | slot、location、来源、enabled、restart_hold_ms | 前端拼：capabilities + 已缓存 bindings/inventory；缺则「—」 |

**串口卡（operate）**

| 行 | 内容 | 来源 |
|----|------|------|
| 标题 | label / com 名 + status | capabilities |
| 端点 | endpoint / port_name | capabilities |
| 运行一行 | `health.state` · holder/busy | 需并入：现 capabilities 有 health；**holder 目前只在 serial.caps.busy** → 前端交叉或后端补字段（见 §4） |
| 动作 | [控制台]（+ 未来 serial_read）；无 power 按钮 | PT9 P2 |

**ADB 卡**：沿用 PT9 P3/P4，本轮不扩。

### 2.3 三种可行方案

#### 方案 A — 全部合并进能力区（无独立电源绑定卡 / 无串口表）

```
┌─ 指纹 ─────────────────────────────────────────┐
├─ 能力（三卡一排）──────────────────────────────┤
│  [ADB]     [串口·health/holder·控制台]         │
│  [电源·开/关/重启]                             │
│    └ 详情折叠：slot/location；admin：绑/解绑   │
│  （多电源则多卡；卡底 admin「绑定新通道」抽屉） │
├─ （无「电源绑定」顶层卡、无「串口」顶层表）────┤
└─ 右栏摘要 ─────────────────────────────────────┘
```

| | |
|--|--|
| **优点** | 单一滚动主路径最短；重复面消得最干净 |
| **缺点** | 绑定 UX 挤在卡内抽屉，多通道 inventory 难排；与 PT4a「页内绑定闭环」表格心智冲突；卡高度膨胀 |
| **改动量** | **L**：`App.vue` 大改模板 ~250–400 行；可能要新抽屉组件逻辑；仍依赖 inventory API |
| **权限** | admin 绑/解绑进卡内菜单；普通用户只见摘要 tag「已绑 CH1」无节点选择器 |

#### 方案 B — 能力区（operate）+ 独立管理面板折叠（configure）★推荐

```
┌─ 指纹 ─────────────────────────────────────────┐
├─ 能力（三卡一排，PT9 §4）──────────────────────┤
│  [ADB]  [串口·health/holder·控制台]  [电源·动作] │
│  电源卡角标：「已绑 bull1 CH1」；无第二套开关   │
├─ [admin] 电源配置 ▸（默认折叠）────────────────┤
│  展开后：节点选择 + 已绑表（无开/关列）         │
│          + 可绑定通道 + 绑定/解绑               │
│  非 admin：整块不渲染；或只读一行「N 路已绑」   │
├─ 串口端口明细 ▸（默认折叠，或删除）────────────┤
│  仅非 power role；展示 health/holder 备份视图  │
└─ 右栏摘要 ─────────────────────────────────────┘
```

| | |
|--|--|
| **优点** | 对齐用户反馈 A/B；PT4a 绑定闭环保留但降噪；改动可渐进；operate/configure 边界清晰 |
| **缺点** | 仍有第二块 DOM（折叠）；admin 展开后信息密度仍高 |
| **改动量** | **M**：前端为主 ~180–280 行；可选小后端（device 维度 bindings、holder 进 capabilities） |
| **权限** | 折叠面板 `v-if="me.role==='admin'"`；普通用户只见能力卡；租约闸仍只挡动作按钮 |

#### 方案 C — 配置全部迁到 CtrlRes；设备页只留能力区

```
设备页：
┌─ 指纹 + 能力三卡（含开关/控制台）──────────────┐
│  电源卡 footer：「去 PowerRes 管理绑定」链接    │
└─ 右栏摘要 ─────────────────────────────────────┘

CtrlRes → PowerRes：唯一绑定/解绑/inventory 台
```

| | |
|--|--|
| **优点** | 设备页最干净；配置职责回归资源台 |
| **缺点** | **回退 PT4a 页内绑定收益**；日常绑通道又要三跳；与已落地「详情页内绑定」产品方向相反 |
| **改动量** | **S–M**（删/藏设备页绑定卡）；产品争议大 |
| **权限** | 设备页无 configure；admin 去 CtrlRes |

### 2.4 推荐

**推荐方案 B**，并与 PT9 同迭代或紧随：

1. 能力区按 PT9：三卡一排 + P1 去假 serial.io + 卡内唯一电源动作。  
2. 「电源绑定」改名为「电源配置」，**默认折叠且仅 admin**；表内**去掉**开/关/重启/补偿开，只留绑定/解绑与配置列。  
3. 底部「串口」表：**默认删除**；若调试需要，改为「端口明细」折叠且 `role∉{power,mode}`。  
4. 头栏「串口控制台」：**保留**（PT9 待拍板倾向「复制」；多口总览仍有价值）。

方案 A 作为「卡数少、几乎无 admin 绑通道」场景的演进；方案 C 仅当产品明确放弃页内绑定再选。

## 3. 去重后的权限与动作矩阵

**角色边界（现状事实，PT4 已核）**：Web 仅 `admin` | `user`；无独立 readonly。串口/电源执行：`admin` 放行；非 admin 须设备活跃租约（`serial.check_access`）。前端 `devicePowerLeaseBlocked`（`App.vue` L2422–2427）用 `holder_email||owner` 近似，与后端租约闸不完全同一字段——实现时应继续以 **API 403** 为准，UI 禁用为辅。

| 动作 | 唯一 UI 入口（推荐 B） | admin | user + 持租约 | user 无租约 | 备注 |
|------|------------------------|-------|---------------|-------------|------|
| 电源开 / 关 / 重启 / 补偿开 | **能力·电源卡** | ✓ | ✓（租约） | ✗（按钮灰 + API 拒） | **从绑定表删除** |
| 查看已绑通道摘要 | 能力卡 tag / 右栏「N 路」 | ✓ | ✓ | ✓ | 只读 |
| 查看 location/slot/来源详情 | 电源卡「详情」折叠 或 配置面板 | ✓ | 可选只读（待拍板） | 可选只读 | 不含按钮 |
| 选择节点 / 看可绑定通道 / 绑定 | **电源配置面板** | ✓ | ✗（不渲染） | ✗ | `POST /api/powerres/bind` |
| 解绑 | 配置面板 | ✓ | ✗ | ✗ | `POST /api/powerres/unbind` |
| 串口控制台 | 串口卡内 + 头栏（复制） | ✓ | ✓（登录即可，与现网一致） | ✓ 登录 | 写锁仍由 serialhub holder 管 |
| 串口 health/holder 查看 | 串口卡内一行 | ✓ | ✓ | ✓ | 自底部表迁入 |
| ADB 白名单动作 | ADB 卡 | 按 PT9 拍板 | 按 PT9 | 按 PT9 | 本轮不改契约 |
| PUT 串口端口配置 | 非设备页主路径（已有 admin API） | ✓ | ✗ | ✗ | `PUT …/serial` |

**取舍结论**：绑定表上的开/关/重启是历史「表即操作台」；能力卡出现后变成双入口。**删除绑定表动作列，保留能力卡**——与「能力区 = 运行操作面」一致，且 `doDeviceCapPower` / `runDeviceSerialAction` 已是真实执行路径。

## 4. 后端数据是否够用

| 需求 | 现有数据 | 判定 | 说明 |
|------|----------|------|------|
| 能力卡展示电源 label/endpoint/status/actions | `GET …/capabilities` power item | **前端可解** | `_build_power_or_mode_item` 已够运行态 |
| 能力卡展示 `power_dev` / `channel` / `slot` / `bound_device_id` | `binding` via `_powerres_binding_view`（L849–864） | **前端可解** | 模板未用，补展示即可 |
| 能力卡展示 `location` / `driver` / `restart_hold_ms` | bindings 经 `_inventory_meta` 有 location/driver（无 hold）；inventory 有 `restart_hold_ms` | **前端可解（拼缓存）** / **可选后端补** | 若删掉电源配置卡的 bindings 预载，则需：① 保留轻量 `GET bindings?device_id=`；或 ② capabilities power item 嵌入 `location`/`restart_hold_ms` |
| 串口卡展示 `health.state` | capabilities item.health；卡未渲染 | **前端可解** | 模板加一行 |
| 串口卡展示 `holder` / busy | 仅 `GET …/serial` → `busy`（L386–392） | **前端可解（交叉）** / **可选后端补** | 交叉：`loadDeviceSerial` 仍拉、不渲染表，把 busy 映射到卡；或 capabilities 增加 `busy`/`holder` 避免双请求 |
| 过滤串口表/能力中的 power | PT9 P1 后端跳过；前端表可 `role` 过滤 | **前端可解止血**；**根因需后端** | 与 PT9 一致：推荐后端 |
| 非 admin 隐藏节点选择与候选表 | 纯 UI `v-if` | **前端可解** | 无需新权限 API |
| 去掉绑定表电源按钮 | 纯 UI | **前端可解** | |
| 按 device 拉本机 bindings（避免 overview×N） | 现仅 `bindings?node_id=`（PT4 §1.3） | **可选后端补（体验）** | 非整合阻塞；现逻辑能用偏慢 |
| 合并 inventory + capabilities 一次查询 | 无 | **不需要本迭代** | 增加耦合；B 方案折叠后 admin 才打 inventory |
| `GET /api/devices/{id}` 的 `serial`/`power_n` | 列表有 `serial.power_n`；详情 `device_info` 有 `serial_ports`/`serial_openable`，**无 power_n** | **前端可解** | 右栏继续用 `devicePowerBindings.length`；或详情附加 flags（可选） |
| 统一 busy loading scope | 前端 | **前端可解** | 删除第二入口后自然消失 |

**结论**：方案 B 的 **MVP 可纯前端完成**（藏/折叠配置面、删双按钮、串口表删或滤、卡内渲染 health、busy 交叉自 `/serial`）。**建议同做的后端**：PT9 P1（必做）+ 可选 `capabilities` 嵌入 power 的 `location`/`restart_hold_ms` 与 serial.io 的 `holder`（减少双请求与折叠依赖）。**不建议**本轮强制合并 inventory∪capabilities 大接口。

### 5.2 验收标准（可执行）

#### 接口 JSON

1. （PT9）仅 PowerRes `role=power` + observed tty 的设备：`items` 无电源冒充的 `serial.io`；恰有一个 `kind=="power"`；observed serial.io `read_only==false`。  
2. `POST …/serial/action` power_* 行为不变（租约/admin）。  
3. （可选）power item 含 `binding.location` 或并列 `powerres.location`；serial.io 含 holder 或文档写明由 `/serial.busy` 交叉。

#### 页面（`#/device/dev_997b70adae` 类页面）

1. **`bull1 CH1`（或等价 label）在全页可视主路径只出现一次**（能力·电源卡）；配置面板折叠时不可见第二次。  
2. **`ttyUSB0`（或等价）只出现一次**（能力·串口卡），且卡内有控制台入口与 health（及 holder 若 busy）。  
3. **任意时刻同一通道只有一个开/关/重启入口**（能力卡）；电源配置表无这些按钮。  
4. **非 admin**：不显示节点选择器、不显示「可绑定通道」、不显示解绑/绑定；无「电源绑定」噪音 alert 或改为极简只读。  
5. **admin**：电源配置默认折叠；展开可完成绑/解绑（回归 PT4a）。  
6. 串口运行列表**不含** `role=power` 行（若保留端口明细折叠）。

## 8. 关键结论摘要

| 项 | 结论 |
|----|------|
| 重复面 | 电源通道 ≤3–4 处；开关 2 套；串口 2 处 + 头栏；配置字段挤在运行卡 |
| 推荐方案 | **B**：能力区唯一运行操作面 + admin 折叠电源配置（无开关）+ 串口表删除或折叠过滤 |
| 动作入口 | 开/关/重启 **只留能力卡**；绑/解绑 **只留配置面且仅 admin** |
| 后端 | MVP **前端可解**；P1 后端必做；location/holder 可选补齐 |
| 待拍板 | 配置面板留页 vs CtrlRes；串口表删 vs 折；非 admin 可见绑定深度；头栏控制台；与 PT9 同 PR 否 |
