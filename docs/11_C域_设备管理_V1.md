# C 域：设备管理（管理员视角）

> 版本 V1 ｜ 配图：`设备管理框图.png`（五块职责）、`Web控制台信息架构.png`（八个一级菜单）
> 上游：`06_子系统清单_V1.md` S3/S7/S8/S10/S11、`07_三大功能模块_V1.md` C1–C5

## 0. 定位

C 域是**管理员的后台**，不是第二个入口：

- 不管申请、不管排队、不发凭据 —— 那些是 A 域
- 只做两件事：**看**（现状是否可信）+ **纠正**（异常是否有人接）
- **只有管理员登录**，普通人零界面

## 1. Web 的八个一级菜单

| 菜单 | 回答什么问题 | 主要内容 |
|---|---|---|
| **1 看板** | 今天还有几台能用 | 按机型的余量表（总数/可用/占用/待验证/故障）；**余量给两个数**：现在能申请几台、排完队还剩几台 |
| **2 设备** | 每台在哪、归谁、什么状态 | 列表 + 单台详情（探测历史 / 身份变更 / 租约历史 / 通知历史）；机型字典与位置规则作为它的子页 |
| **3 占用** | 谁在用、还要用多久 | 按人 / 按机型两种视角；到期前 10 分钟标黄、超期标红 |
| **4 排队** | 谁在等、等了多久 | 每机型一条队列：队首、人数、最长等待、今日唤醒次数 |
| **5 异常 / 待修复** | 坏了的那几台谁去修 | 按 `owner` 分组 + 三个小队列（身份待确认 / 冲突待裁定 / 30 天没通的待清理） |
| **6 凭据** | 发出去的 token 还活着吗 | 一人一行：邮箱、token 尾号、有效期、是否用过、最后调用；动作：续期 / 吊销 / 补发 / 一键摘人 |
| **7 审计** | 这件事是谁干的 | 全量流水，按人/设备/时间/动作检索；强制回收、改位置、改 owner 必须可追 |
| **8 设置** | 系统自己还健康吗 | 巡检周期、通知渠道、SMTP、去重窗口、管理员账号；**系统健康**：MCP 在不在、上一轮巡检何时跑完、邮件成功率 |

两条排布原则：

1. **凭据不进「设置」**。它天天要动，是运营页不是配置项，必须独立一级菜单——塞进设置里，等于每次发凭据都要多点两层。
2. **机型字典、位置规则挂在「设备」下**，不单列。它们是主数据，不是独立业务。

## 2. 巡检运行状态

你问的"是不是上次巡检的状态"——是，而且要比"上次时间"更细。**一轮巡检就是一条运行记录**。

### 2.1 一轮记录里有什么

| 字段 | 用途 |
|---|---|
| `run_id` / 开始 / 结束 / 耗时 | 判断这轮是不是跑超时了 |
| 扫描台数 / L3 数 / suspect 数 / offline 数 | 四个数放在一处，一眼看本轮结果 |
| 本轮新增异常（与上一轮的 diff） | **只看新增**，已经坏着的不再重复制造焦虑 |
| 失败明细（设备 → 级别 → 原因） | 点得进去，直达单台详情 |

### 2.2 页面上要显示的四块

1. **上次巡检**：绝对时间 + 相对时间（"12 分钟前"）
2. **下次巡检**：预计时间
3. **最近 24 小时通过率曲线**：看趋势，不看单点
4. **按机型的通过率**：某个机型集体掉线，通常不是设备坏，是固件或镜像的问题 —— 这一列最能指向根因

### 2.3 最危险的情况：巡检自己停了

这是整套系统里最容易被忽略、后果最重的一条：

> 巡检 worker 挂了，或者每轮都跑超时，**看板会一直显示"最后已知状态"——全是绿的**。
> 等人来申请、连不上，才发现设备三个月前就掉线了。

所以必须做**巡检心跳**：

- 连续 **2 个周期**没有产生新 `run` → 高优先级告警给管理员
- 看板顶部挂持久红条：**"数据可能过期：最后更新 14:20"**
- 红条不随刷新消失，直到有新 run 产生

这条比任何单台设备告警都重要，因为它会让所有基于看板的判断同时失效。

### 2.4 单台探测历史

在设备详情页按时间列出：级别变化（L3 → L1 → L0）、每次探测的耗时、失败原因。这是排障时最有用的一页——能看出"是慢慢坏的，还是突然断的"。

## 3. 通知流水与闭环

### 3.1 一条通知的生命周期

```
事件 → 通知任务 → 接收人（1~N 个）→ 每个接收人各自一条送达记录
```

**关键点：状态是记在接收人身上的，不是记在通知上的。**

发给 3 个人，可能 2 个送达、1 个失败。只在通知上记一个"已发送"，等于把失败吞掉了。

| 状态 | 含义 |
|---|---|
| `pending` | 待发 |
| `sent` | 已提交给渠道 |
| `delivered` | 渠道确认送达 |
| `failed` | 渠道报错，附错误码 |
| `timeout` | 超过 5 分钟无回执 |
| **`acked`** | **接收人确认"我去处理"**（这是唯一能证明人真的看到了的状态） |

### 3.2 事件类型

| 事件 | 发给谁 |
|---|---|
| 设备掉线 | `owner` + 当前占用人 |
| 设备恢复 | 同上（闭环，别让人白跑一趟） |
| 身份冲突 / 待确认 | 管理员 |
| 租约超期未还 | 占用人 + 管理员 |
| 排队被唤醒 | 队首那个人 |
| 凭据即将到期 | 管理员（可批量续） |
| 设备被注销 | 正在排队等它的人 |
| **巡检停摆** | 管理员（最高优先级） |

### 3.3 重试与降级

- 单渠道失败 → 重试 2 次（间隔 30 秒 / 5 分钟）
- 仍失败 → **降级到备用渠道**（企微 → 邮件）
- 全部失败 → 页面上标红，管理员可手动重发
- 每条流水记渠道、时间、错误码 —— 后期排查"为什么没人知道"就看这页

### 3.4 「发出去了」不等于「人收到了」

这是通知系统最常见的自欺：API 返回成功，人根本没看。所以补两个机制：

1. **acked 确认**：通知里带一个"我去处理"的按钮，点一下才算真的接住了
2. **未 acked 升级**：设备持续 offline 超过 24 小时且无人确认 → 升级告警给管理员

没有这两条，通知就只是"系统觉得自己通知过了"。

### 3.5 恢复要闭环

设备恢复后，**在同一条通知链上补发"已恢复"**，并把告警关单，同时记下响应时长（从 offline 到恢复）。

这个时长数据是有价值的：哪个 owner 的设备总是修得慢、哪类机型故障恢复最费时，都从这里看。

### 3.6 告警风暴控制

50 台设备同时掉线（交换机断电、机架断电），如果发 50 条通知，人就再也不看通知了。

| 聚合规则 | 效果 |
|---|---|
| 同设备 **2 小时**内合并 | 反复抖动只算一次 |
| 同位置前缀（`302-R*`）**15 分钟**内合并 | 18 台同时掉线 → 一条"302 机架整段失联 18 台" |
| 合并后仍可展开明细 | 点开能看到具体是哪 18 台 |

**聚合是按位置而不是按机型**：同一个机架、同一个交换机下面一起掉，才是"一处故障"；不同房间同时掉几十台，那更可能是巡检自己出了问题——那种情况走 §2.3 的心跳告警。

## 5. 三条边界（越界就会和 A 域打架）

1. **C 域只读租约、不改租约** —— 强制回收是唯一例外，且必须留痕 + 通知占用人
2. **巡检只改健康状态，不动租约** —— 掉线不等于释放，占用人回来还能接着用
3. **主数据（机型 / 位置 / owner）只由管理员改，Agent 只读** —— 否则台账会被两头改乱

## 7. Web 与 MCP 的暴露面对照

### 7.1 原则：数据层共用，暴露面分级

两条要同时成立，缺一条就会出问题：

1. **数据层必须共用** —— Web API 与 MCP Server 同进程、同一套 domain service、同一个库。这样"Web 说还有 3 台、MCP 说还有 5 台"这类分歧在结构上不可能出现。
2. **暴露面不做全量镜像** —— Web 是管理员的工作台，MCP 是 Agent 的决策入口，两者需要的字段不是一回事。为了"都能查"而把 Web 的内部字段全给 MCP，只会让 Agent 拿到它不该有的信息。

### 7.2 三档划分

| 档 | 含义 | 典型内容 |
|---|---|---|
| **可查** | Agent 做决策必需的 | 机型余量、设备列表、健康级别、我的租约、排队情况、我自己的配额 |
| **脱敏可查** | 要状态，不要身份 | "设备 A 占用中，预计 12:30 释放"——不给占用人是谁 |
| **不可查** | 管理动作与他人隐私 | 凭据发放 / 续期 / 吊销、他人租约明细、审计全表、通知流水、系统配置 |

### 7.3 八个页面 → MCP 工具对照

| Web 页 | MCP 是否可查 | 对应工具 |
|---|---|---|
| 1 看板（机型余量） | ✅ | `res_list_products` 扩展返回：总数 / 可用 / 占用 / 排队数 |
| 2 设备（列表 + 详情） | ✅ | `res_list_devices`（带 level、最后探测时间）+ **新增** `res_device_info` |
| 3 占用 | ⚠️ 脱敏 | 同上，只给 `occupied` 与 `free_at`，不含人名 |
| 4 排队 | ✅ | `res_ticket`（已有） |
| 5 异常 / 待修复 | ⚠️ 部分 | 只给单台健康级别；**"待修复队列"是管理员工作台，不给** |
| 6 凭据 | ⚠️ 只给自己 | **新增** `res_whoami`：我的配额、凭据有效期、我的租约数；别人的一律不给 |
| 7 审计 | ❌ | 不给。管理动作流水永不对 Agent 开放 |
| 8 设置 | ⚠️ 只给健康 | **新增** `res_health`：服务是否正常 + **数据最后更新时间** |

### 7.4 建议新增的三个工具

| 工具 | 返回什么 | 为什么需要 |
|---|---|---|
| `res_device_info(device_id)` | 单台详情：机型、位置、状态、健康级别、当前占用（脱敏）、串口列表 | Agent 申请前想确认"这台到底是不是好的" |
| `res_whoami()` | 我是谁（邮箱）、配额上限、已用几台、凭据何时到期 | Agent 能自己判断"我还能不能再申请"，不用非要报错才知道 |
| `res_health()` | MCP 服务状态、最近一轮巡检时间、**数据新鲜度** | 呼应 §2.3：巡检停摆时清单是旧的。Agent 应该能自检"我拿到的数据是不是过期了"，而不是盲目相信一份三小时前的列表 |

`res_health` 这条最容易被认为"没必要"，但它解决的是一个真实问题：**当系统自己坏了，Agent 是最后一个知道的**。

### 7.5 为什么占用人要脱敏

一个 Agent 调一次 `res_list_devices` 就能拿到全公司 500 台设备的占用人名单——等于它能画出"谁在做什么项目、哪个组在扩产线"。

这不是安全问题（局域网内本来就能 adb connect），是**没必要**：Agent 只需要知道"这台现在能不能用、什么时候空"，不需要知道是谁在用。

管理员在 Web 上能看到人名，Agent 在 MCP 上只看到状态和时间——这才是对的。
