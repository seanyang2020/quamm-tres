# B 域：设备注册（Agent 发起）

> 版本 V1 ｜ 上游：`04_设备注册与身份识别方案_V1.md`（信号与分型的原理）、`07_三大功能模块_V1.md` B1–B5
> 本文讲**操作流程与工具契约**，04 讲**打分原理与分型**，两份配合看。

## 0. 这一域要解决什么

一句话：**Agent 报一个 IP，系统把它变成台账里一条可信的设备记录。**

不是填表，是"证明这台设备是哪一台"。所以整条流程的重点不在字段多少，而在**三件事**：

1. 连得上吗（L3）
2. 是哪一台（强锚比对）
3. 放在哪（位置编号，只有人能给）

三件都成立才入池。缺任何一件都不入池，但也不丢——挂在待修复或待认领列表里。

## 1. 形态变了：从"管理员录入"到"Agent 发起"

原来 04 文档写的入口是管理员在 Web 上填表。现在改成 **Agent 通过 MCP 发起**，理由和你对 A 域的口径一致：**MCP 既管申请者，也管资源**。

于是职责划分变成：

| 角色 | 做什么 |
|---|---|
| **Agent** | 报 IP、调工具、把表单转给人 |
| **系统** | 自动探测、预填、比对台账、给出三种判定 |
| **人** | 只补两个字段：**位置编号**、**维护责任人**；可选做一次点亮核对 |
| **管理员** | 不看单台设备的注册过程，只在 Web 上看"最近注册了哪些、有没有冲突" |

**人不填表**——人只填空着的那两格。这是这一域的核心设计取向：探测能拿到的一律自动填，人不做搬运工。

### 1.1 两条入口，同一套判定

你定的两条通道都保留，但不是两套系统：

| | 通道 A：管理员 Web 批量录入 | 通道 B：Agent MCP 注册 |
|---|---|---|
| 适用 | 新到货一批、没人会调 MCP 的时候 | 现场有 Agent，直接报一个 IP |
| 顺序 | **先填后探**：填 IP/MAC/设备名 → 点「探测」→ 对账 → 补位置 | **先探后填**：只报 IP → 探测 → 补位置 |
| 批量 | 一次贴 50 行 CSV | 一次一台 |
| 归属 | `registered_by` = 管理员 | `registered_by` = token 归属人 |

**代码上只有一个注册服务**：Web 上的「探测」按钮和 MCP 的 `res_device_probe` 调的是同一个函数，后面的打分、判定、入池也是同一段逻辑。

这条不能松——否则会出现"Web 认为是新设备、MCP 认为是老设备"的分歧，台账两边各记一份，谁也说不清哪条对。这与 A 域"双入口共用逻辑"是同一条原则。

### 1.2 三个身份字段不能混

| 字段 | 含义 | 谁填 |
|---|---|---|
| `registered_by` | **谁把设备搬进系统**（管理员，或某个持 token 的人） | 系统自动记 |
| `register_channel` | `admin_web` / `mcp_agent` | 系统自动记 |
| **`owner`** | **谁对这台设备负责**：坏了找他、掉线通知他 | **人必填** |

前两个是溯源用的，第三个才是真正干活的。

**注册人可以不是责任人**：管理员批量录入 20 台，责任人是分到各工位的那几位工程师。所以 `owner` 必须能单独指定，不能硬绑 `registered_by`（UI 上可以默认填注册人，减少输入）。

`owner` 同时是巡检通知的锚点，**必须和 I 域的"维护责任人"是同一个字段**，不能建两套。

### 1.3 一条原则：谁注册都不改变共享属性

个人注册进来的设备，照样进公共池，谁都能申请。`registered_by` 只用来追溯设备来源，**不构成任何优先权、独占权或"我的设备"概念**。

否则设备会慢慢变成私人资产，池子就空了——这比"台账被乱写"更伤。

真正需要守住的是：**每台设备必须有 owner**。有人负责，就能维护、就能通知、掉了能找人；没人负责的设备，进池也是负担。所以 `owner` 是唯一强制的人工输入（连同位置编号）。

### 1.4 「允许大家共享」必须配的四个动作

这条放开了供给——设备不再只能由管理员搬进来，**任何持 token 的人都能把自己手上的设备共享出去**。但供给一旦放开，就必须能收得回来，否则池子会脏。

| 动作 | 为什么必须有 | 怎么走 |
|---|---|---|
| **注销** | 设备搬走、报废、归还仓库 | 与注册对称：Web 一键注销 / MCP `res_device_unregister`。**注销前必须无有效租约**：有租约时要么等释放，要么管理员强制回收后再注销 |
| **转移 owner** | 工位调动、人离职、责任移交 | 管理员改 `owner`，或新 owner 在 MCP 里确认接管；留流水 |
| **重复注册拦截** | 两个人注册同一台设备 | 拒绝，并明确告知：该设备已由 X 登记（位置 302-R2-05，owner 为 Y）。如需接管，请让原登记人注销，或找管理员转移 |
| **摘除** | 误注册、僵尸记录、克隆件 | 管理员在 Web 一键摘，连带清掉该设备的身份待确认记录 |

**最容易漏的是第一条：注销与注册对称。** 只开注册不开注销，台账只会越滚越大，最后没人敢清理——因为删不掉，只能堆着。所以两个入口都得能注销，而且注销要简单到点一下。

### 1.6 谁能解注册，什么时候能解

**权限**（只给这两种人，不给 `owner`）：

| 谁 | 能注销什么 | 理由 |
|---|---|---|
| **注册人**（`registered_by`） | **自己登记的设备** | 就是他搬进来的，想拿回去就该拿得回去 |
| **管理员** | 任意设备 | 兜底：误注册、离职遗留、报废 |

`owner` **不给注销权**。因为 `owner` 是维护责任（设备坏了找他、掉线通知他），不是资产处置权。两个权力分开，避免"我负责修它所以我就能摘它"。

**前置条件：不能有活动租约。**

| 情形 | 行为 |
|---|---|
| 无人占用 | 立即注销，状态转 `retired`，移出可用池 |
| 有活动租约（别人正在用） | **拒绝**，返回 `HAS_ACTIVE_LEASE` + 占用人 + 预计释放时间 |
| 有活动租约，但注册人坚持要收回 | 标 `pending_removal`，**挂待下架**：不再接受新申请，等当前租约正常结束或到期后自动注销 |
| 管理员强制 | 先 revoke 租约（会通知占用人），再注销 |

**为什么不让它直接抢**：租约的意义就是"这段时间这台设备归你"。如果注册人能随时摘走，正在跑长任务的人会莫名其妙断掉。要收回可以，但排在队里等。

**注销不是删除。** 记录留在库里（`retired`），因为审计和统计要用。重新注册时：

- 强锚（MAC / SN / asset_tag）命中这条已注销的记录 → **复活它**（复用原 `device_id`，改回 `available`），历史不断裂
- 强锚不命中 → 建新记录

这条很关键：否则"注销再注册"会造出两条记录，同一台设备的占用历史被掰成两段，统计就不准了。

**两条附带的处理**：

1. 注销时，**排队等这台设备的人要收到通知**（"该设备已下架，请改申请其它同类设备"），否则他们会一直等一台不会回来的设备
2. 注册人离职 / token 被吊销后，他登记的设备**不跟着失效**——设备还在场地里，只是没人能替他注销了，改由管理员处置（`owner` 继续负责维护）


### 1.5 一个要定的小事：怎么区分公司资产和私人设备

"谁都能共享"的副作用是：有人会把自己桌上的板子、甚至自己的开发机注册进来。技术上拦不住，也不该硬拦。

建议靠**位置编号**区分，不额外加字段：

| 特征 | 判定 |
|---|---|
| 位置编号是机架位（`302-R2-05`，有房间有排有号） | 视为公司资产，在场地内 |
| 位置编号填"工位""临时""桌面" | 视为个人提供，管理员可筛出来单独看 |

不拦、不拒，但 Web 台账要能一键筛出"无正式位置"的设备，让管理员一眼看到混进来的是什么。这比加一个"资产/个人"字段省事，也不依赖人去判断。



## 2. 四个 MCP 工具

注册不是一次调用能完成的：探测完要等人去查位置编号，人可能离开几分钟。所以拆成**两段式**，中间用 `form_id` 串起来。

### 2.1 `res_device_probe` —— 探测并出表

```json
// 入参
{ "ip": "10.20.3.47", "hint_model": "QM10XD", "hint_position": "302-R2-05" }

// 出参
{
  "form_id": "reg_7f3a91",
  "expires_at": "2026-11-07T23:52:00+08:00",
  "probe": {
    "ip": "10.20.3.47",
    "adb_port": 5555,
    "level": "L3",
    "mac": "aa:bb:cc:dd:ee:ff",
    "sn": "SN2024A1234",
    "model": "QM10XD",
    "android_version": "13",
    "build_fingerprint": "qti/qm10xd/...",
    "has_screen": true,
    "has_led": false,
    "asset_tag": null,
    "serial_ports": [{"port": "/dev/ttyUSB0", "role": "console"}]
  },
  "identity_match": {
    "result": "new",
    "matched_device_id": null,
    "matched_by": null,
    "signals": {"mac": 90, "sn": 90, "asset_tag": 0, "position": 0}
  },
  "need_from_human": ["position_code", "owner"],
  "optional": ["flash_confirm"],
  "next": "请让使用者提供位置编号（格式 302-R2-05）与维护责任人，然后调用 res_device_register 提交 form_id"
}
```

三点必须写死：

- `hint_model` / `hint_position` 只是提示，**不能直接采信**：探测结果与提示不一致时，以探测为准并在返回值里标 `hint_conflict`
- `next` 字段是**给 Agent 的行动指令**，不是给人看的说明。Agent 会照着它做事，所以要写成祈使句，明确"下一步让谁做什么"
- `form_id` **30 分钟有效**，同一 IP 重复 probe 返回同一个 `form_id`（幂等，避免 Agent 重试造出一堆表单）

### 2.2 `res_device_register` —— 提交并受理

```json
// 入参
{
  "form_id": "reg_7f3a91",
  "position_code": "302-R2-05",
  "owner": "yangxiongwei",
  "model_class": "QM10XD",        // 可选，人可纠正探测结果
  "note": "新到货第二批"
}

// 出参
{
  "device_id": "dev_0a3f",
  "status": "available",
  "matched_as": "new",             // new | existing
  "warnings": [],
  "next": "设备已入池，可用 res_list_devices 查询；申请时用 res_apply 指定 device_id 或 resource_group"
}
```

**位置编号和责任人任何一项缺失，都拒绝提交**，返回 `MISSING_FIELD` 并附上还缺什么。这条不能松——一个没位置的设备入池，等于给全组埋了一个找不到的坑。

### 2.3 `res_device_flash` —— 让设备亮起来

```json
// 入参
{ "form_id": "reg_7f3a91", "duration_sec": 8 }

// 出参
{
  "flash_id": "flash_2b81",
  "confirm_code": "4718",
  "how": "screen",                 // screen | led | sound | none
  "next": "请使用者确认：那台设备屏幕上是否显示 4718 并且正在闪烁？确认后调用 res_device_confirm 回填该码"
}
```

**这里比"你看到它闪了吗"多做了一步**：屏幕上同时显示一个 **4 位随机码**，人要回填这个码。

- 只问"闪了吗"，人容易凭印象答"是"
- 回填码，必须真的看着那台设备才能答对
- 带屏机型都能做到；只有 LED 的机型退化为"闪 3 长 2 短"这类可区分的节奏；两样都没有的机型 `how=none`，直接跳过

**它的定位要说清**：这是**帮人确认对应关系**的辅助手段（防手滑选错设备），不是防恶意。技术上 Agent 自己 `screencap` 也能读到那个码。符合"服务不是门禁"的定位，不用加固。

### 2.4 `res_device_confirm` —— 回填确认码

```json
// 入参
{ "flash_id": "flash_2b81", "code": "4718" }
// 出参
{ "verified": true, "confidence": "high" }
```

对不上返回 `verified: false` 并允许重试 2 次，第三次要求管理员介入。确认结果记入 `identity_claim.confidence`，**不影响是否入池**——跳过核对照样受理，只把设备置信度标成 `medium`。

## 3. 探测能给什么、给不了什么

| 字段 | 来源 | 可靠性 |
|---|---|---|
| MAC | `ip link` / `cat /sys/class/net/*/address` | 高，但**多网卡时要选对**那个有线的 |
| SN | `getprop ro.serialno` | 部分机型稳、部分机型重启会变 |
| 机型 | `getprop ro.product.model` | 中，只能对上"机型类别"，对不到"具体那一台" |
| 系统版本 | `getprop ro.build.version.release` | 高，但刷机就变 |
| 硬件 ID | `/proc/cpuinfo` + 器件型号 | 中，同批次可能重复 |
| asset_tag | `cat /persist/asset_tag` | **有则最强**（前提是镜像里写了这个文件） |
| 位置编号 | —— | **探测不到，只能人给** |
| 责任人 | —— | **只能人给** |

一条重要提醒：**能探测到不等于能当主键**。MAC 会因擦 data 而变，SN 部分机型不稳，asset_tag 依赖镜像支持。所以仍然是 04 文档那套"强锚打分 + 三档决策"，探测只是把分数算出来的手段。

### 3.1 机型不是自由填的

`model_class` 必须是**机型字典（`product_type`）**里的值——预置、有限、由管理员在 C 域维护，**不在字典里的一律拒绝**。

理由：公司产品线是有限的，机型属于主数据，不是自由文本。一旦放开，同一台设备会被写成 `QM10XD` / `qm10xd` / `QM10XD-Board` / `QM10XD开发板` 四种，按机型统计就废了。

探测结果要过一道映射：

| 探测到的 `ro.product.model` | 处理 |
|---|---|
| 命中字典中的 `model_pattern` | 自动填 `model_class` |
| 未命中 | 填 `unknown_model`，**不阻塞注册**，同时提示"请在机型字典中新增该机型" |
| 与 `hint_model` 冲突 | 以探测为准，标 `hint_conflict` 让人确认 |

`unknown_model` 的设备照样可以入池（能跑 adb 就能用），只是申请时按机型筛选看不到它——这比拒绝注册合理，也比瞎猜成某个已知机型安全。


## 4. 三种受理结果

| 结果 | 触发条件 | 动作 | 为什么不这么做会出事 |
|---|---|---|---|
| **A 认定为已有设备** | 强锚（asset_tag / 硬件 ID / MAC / SN）唯一命中一条记录 | 更新该记录的 IP、版本、位置，**不新建** | 不这么做，擦一次 data 就多一条记录，旧记录永远在线变僵尸，历史统计全断 |
| **B 新建一台设备** | 三项强锚都查不到，且位置编号不重复 | 建新记录，位置编号成为它的主锚 | —— |
| **D 登记但不可用** | 探测停在 L0 / L1 / L2 | 照样建记录，状态 `pending`，绑好位置和串口，**不进可用池** | 不登记的话，人查好的位置和责任人白填了，下次还得重来 |
| **C 拒绝受理** | 见下 | 返回明确原因和冲突对象 | 只说 error，Agent 会反复重试，人也不知道怎么修 |

**结果 C 的三个具体情形**：

| 码 | 情形 | 返回给 Agent 的话 |
|---|---|---|
| `IP_TAKEN` | 该 IP 已属于另一台已注册设备 | 该 IP 属于 `dev_xxx`（位置 302-R1-03）。如果确实是同一台换了 IP，请调 `res_device_rebind`；如果是新设备，请换一个未被占用的 IP |
| `ANCHOR_CONFLICT` | MAC / SN 命中另一条记录，但 IP 不同 | 该 MAC 已登记为 `dev_yyy`（位置 305-R1-02）。可能是换板 / 克隆 / 搬位置，需管理员确认后再合并 |
| `POSITION_DUP` | 位置编号已被占用 | 302-R2-05 已分配给 `dev_zzz`。请核对标签，或提供一个新的位置编号 |
| `FORM_EXPIRED` | 超过 30 分钟未提交 | 表单已失效，请重新调用 `res_device_probe` |

`ANCHOR_CONFLICT` 是唯一必须人工介入的——因为无法自动判断是"换板"还是"克隆"，判断标准是"能不能靠强锚证明是同一台"，这正是 04 文档五种漂移场景的落点。

## 5. 探不到也能登记，只是不可用

原来这一版写的是"L0/L1/L2 直接拒绝"。按你的口径改掉：**注册这个动作不做真假校验**——探不到照样落一条记录。

但要把两件事分开，这是这一节的全部要点：

| | 登记（进台账） | 入池（可被申请） |
|---|---|---|
| 门槛 | 位置编号 + `owner` 齐了就行 | **必须 L3** |
| 探不到时 | 照常登记，状态 `pending` | 不放入池 |
| 谁能看见 | 管理员、`owner` | 所有人（含所有 Agent） |

所以**不会出现"占了坑却连不上"**：`pending` 设备在申请者眼里根本不存在。

四级差异仍然要逐级写清，因为维护动作完全不同：

| 级别 | 现象 | 返回的维护提示 |
|---|---|---|
| L0 | ping 不通 | 设备没上电或不在网段，先确认物理连接 |
| L1 | 端口不通 | adbd 没起，或 data 被擦导致 5555 未开，需人工接串口恢复 |
| L2 | 端口通但 unauthorized | adbkey 没授权，推一次公钥即可；或预置 adbkey 的镜像没刷上 |
| L3 | shell 可用 | 通过，可直接入池 |

**转正机制**：`pending` 设备每轮巡检会重跑一次探测，**连续 1 轮 L3 就自动转 `available`**，并在审计里记一笔"自动转正"。不是等人来点，是系统自己发现它通了。

**"虚假设备"不用专门防**：不加"真假校验"这道门槛，因为成本高还容易误伤（真设备 momentary 掉线也会被当成假的）。改为靠时间筛：

- `pending` 超过 **30 天从未通过 L3** → 自动进管理员的「待清理」列表
- 管理员一眼看到"这些设备从登记那天起就没连通过"，一键摘除
- 这个列表本身就是天然的真假过滤器，不需要额外规则

这也正是你说的"毕竟有实际探测手段"——探测每轮都会发生，假设备会自己浮出来，不必在入口处卡。


## 6. 位置编号规则（唯一强制的人工输入）

格式定为 **`房间-排-位`**，如 `302-R2-05`：

- 房间：三位数字
- 排：`R` + 一位数字
- 位：两位数字
- 全局唯一，入库时建唯一索引
- 格式不符直接拒绝，不给人"先随便填一个"的机会

为什么卡这么死：位置是**唯一一个不依赖设备自身状态的强锚**。MAC 会被擦、SN 会变、asset_tag 要靠镜像，只有墙上的标签和编号不会变。所以它必须格式化、唯一化、并且上线前盘库一次。
