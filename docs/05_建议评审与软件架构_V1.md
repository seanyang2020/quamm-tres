## 2. 三个必须补的风险（你没提，但会出事）

### 2.1 ADB 5555 是无认证端口（**本期降级：局域网内使用，接受风险，仅记录**）

网络 ADB 一旦开了 tcp 5555，**任何能路由到这台设备的人，不需要任何密码就能 `adb connect` 并拿到 shell**。750 台设备 = 公司网内 750 个无认证的高权限入口。这是整个方案最大的安全暴露面，而且系统层面无法消除。

必须做（P0，网络侧配合）：

1. 测试设备放**独立 VLAN / 独立网段**，与办公网隔离。
2. 交换机 ACL 只放行三类来源：中心服务所在机器、授权开发机（可经跳板）、巡检器。
3. 若暂时做不到隔离，**至少**在路由层限制 5555 的访问源，并在系统里完整记录"谁申请过哪台设备"，做到事后可追溯。
4. 这条要写进上线前置条件清单：**没有隔离就不上线**，不是"以后再说"。

### 2.2 data 区是单点，误刷一次就失联

钩子和 adbkey 都在 data 区，"不刷 data"目前只是纪律。一次误操作就会同时丢掉钩子和 key，设备从"可用"变"失联"，而且现象极像硬件坏（ICMP 通、端口不开），现场很可能直接把好板子换掉。

必须做：

| 措施 | 说明 |
|---|---|
| 刷机工具层拦截 | 在刷机脚本里**硬性禁止** data 分区，参数里出现 data 直接报错退出。不能只靠文档纪律 |
| 系统侧识别 | 巡检发现"L3 → L1 且持续 2 轮"判 `suspect_data_wiped`，通知文案直接给恢复指引 |
| 恢复手册 | 重刷钩子 + 重放 adb_keys 的步骤写进维护手册，避免当作硬件故障处理 |

### 2.3 位置编号上线前必须盘库一次

位置编号当强锚的前提是"贴对了、系统里对得上"。如果标签贴错、或者系统里的位置与实际不符，自动匹配会把两台设备认错 —— **比没有锚更糟**，因为错得很自信。

必须做：上线前做一次全量盘库（现在 750 台没有历史台账，正是好时机）：
- 每台贴资产标签，登记位置编号
- 采集 MAC / SN 现场录入
- 盘完这一遍，位置锚才可信，后续才能自动匹配

## 3. 两处建议调整

### 3.1 主键：内部 `device_id` + MAC 唯一索引

见 04 文档 §4.1 的全擦推演。总结：**语义上"MAC 唯一"完全满足你的要求，但把它做成表主键会在全擦那天把历史记录撕成两半**。用唯一索引能达到同样的约束力，且能挂住标识漂移。这条已标为待确认（04 文档 G1），由你拍板。

### 3.2 进程模型：Web API 与 MCP 必须同进程

这是本次评审新增的一条，也是架构图上体现的。

**问题**：Web 的实时看板靠 WebSocket 推送，推送发生在 API 进程里。如果 MCP Server 是另一个独立进程，那么 Agent 通过 MCP 释放设备后，API 进程并不知道，Web 看板要么不更新，要么得靠跨进程通信（PG NOTIFY / 消息队列 / 轮询事件表）来补。

**结论**：

| 方案 | 评价 |
|---|---|
| 同进程、两个端口（:8080 / :8765） | **推荐**。事件总线在进程内，天然同步；且强制两个入口共用同一套 domain 代码，"双入口一致"变成结构保证而不是人为约定 |
| 拆两个进程 + PG LISTEN/NOTIFY | 可行，但多一层机制要维护，且容易出现"通知丢了看板不更新" |
| 拆两个进程 + 轮询事件表 | 延迟从 2s 退化到轮询周期，不满足看板要求 |

代价：MCP 与 Web 共享进程资源。但 750 台、几十个并发用户与 Agent 的量级，单进程完全够（QPS 极低，瓶颈在 ADB 探测而不是 API）。将来真要拆，加 PG NOTIFY 即可，不影响现在的代码结构。

## 5. 分层职责

| 层 | 组成 | 职责 | 不该做的事 |
|---|---|---|---|
| 客户端 | Web SPA（Vue 3）、MCP 客户端 | 展示、交互、调工具 | 不缓存状态当判定依据 |
| 接入 | Nginx、Web API(:8080)、MCP Server(:8765) | 鉴权、路由、参数校验、协议适配 | 不做业务判断 |
| 应用 | Domain Service + 8 个模块 | 全部业务规则与状态变更 | 不直接拼 SQL、不发通知 |
| 数据 | PostgreSQL + 文件日志 | 持久化、唯一约束、事务 | 不承载业务逻辑 |
| 外部 | 设备池、SerialBridge、企微/飞书 | 被调用 | 本系统不代理其流量 |

**8 个模块的分工**（对应图中编号）：

1. **资源目录与注册** — 设备/串口/位置编号的增删改、认领、下线、分组。
2. **身份识别与匹配** — 采集 MAC/SN/硬件ID/资产文件，打分、漂移判定、冲突检测、待认领。
3. **租约引擎** — TTL、续约、宽限期、强制回收、幂等、原子授予。
4. **队列服务** — 组队列/设备队列、优先级 + FIFO、offer 窗口、顺延、票据。
5. **巡检与健康** — L0–L3 四级探测、连续 2 轮判离线、data 被擦识别、恢复上线。
6. **通知网关** — 企微/飞书模板、责任人路由、去重。
7. **审计与报表** — 只追加流水、利用率聚合、导出。
8. **Worker**（独立进程）— 巡检 30min、租约扫描 10s、网段发现 30min、到期提醒。

## 7. 给开发的 6 条实现约定

1. **双入口同一方法**：Web 的"申请"与 MCP 的 `res_apply` 调同一个 service 函数，只传入参来源不同。
2. **授予在单个事务内完成**：查空闲 → 锁行 → 写租约 → 更新设备状态 → 发事件，全部一个事务，禁止分步提交。
3. **事件先落库再推送**：推送失败不影响业务正确性，看板下次拉取能补上。
4. **worker 单实例锁**：`pg_try_advisory_lock`，防止多副本重复巡检造成重复告警。
5. **时间统一 UTC 存储**，展示层转 +08；所有到期判定以服务端时间为准。
6. **幂等键落库**：同一 holder + 同 target + 24h 内重复申请，返回同一结果，不产生第二条记录。
